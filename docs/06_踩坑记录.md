# 06_踩坑记录

> 四段式：现象 / 原因 / 解法 / 预防。踩到即记，写完把能沉淀的预防措施补进 `01_开发规范`。

## 008 Figma 描边 inside 不占空间，CSS border 外扩占位

- **现象：** 按 Figma 标注的 padding 实现后，所有带边框容器的视觉间距都比设计稿宽 1~2px（如主窗口 padding 6 看着像 8）。
- **原因：** Figma 描边（stroke）默认 inside 对齐、不占布局空间，标注 padding 6 中有 2px 被描边占用；CSS `border` 在 padding 之外另占空间，`border 2px + padding 6px` 视觉就是 8px。每个带边框容器都差一个边框厚度。
- **解法：** 组件线条一律用 `box-shadow: inset 0 0 0 {宽}px {色}` 模拟（不占布局空间，与 Figma inside 描边逐像素一致）；hover/选中换色改 shadow 即可，还省掉了"透明边框占位防抖动"的 hack。
- **预防：** 已写入 `01_开发规范` 第 4 条——UI 组件禁止用 `border` 画设计线条，统一 inset box-shadow（真正分隔内容用的分割线另议）。

## 007 无边框窗口阴影：DWM 路线全部不可靠，终局为 CSS 阴影

- **现象：** 无边框 + 透明窗口要恢复阴影与 12px 圆角，三轮系统 API 方案均翻车：① window-shadows crate（DwmExtendFrameIntoClientArea 1px margins）窗外多 1px 直角线框，且其 rwh 0.5 与 tauri 的 0.6 类型不通用；② tauri 内置 `shadow: true`（tao 恢复 WS_THICKFRAME 换 DWM 阴影）Win11 顺带画 1px 主题边框（DWMWA_BORDER_COLOR=NONE 可抑制）与 8px DWM 圆角（DWMWCP_DONOTROUND 可禁）；③ 即使抑制后，顶边线条、圆角外小块底色等残留仍在——与系统合成器斗，边角永远有漏。
- **原因：** Windows 透明分层窗口的边框/圆角/阴影由 DWM 按自己的规则参与绘制，API 只能抑制不能根除。
- **解法（终局）：** 窗口完全不依赖系统装饰——`shadow: false` + 全透明，HTML 根容器内缩 20px 作阴影带，圆角与 box-shadow 纯 CSS 绘制。视觉跨平台 100% 一致、零平台分支代码；mac 同样适用（关系统阴影即可）。已知代价：阴影带内点击落在本窗口（Electron 系应用普遍如此）。
- **预防：** 无边框窗口的装饰（圆角/阴影/边框）一律 CSS 自绘，不碰 DWM 魔改；窗口原始尺寸 = 可视尺寸 + 阴影带 ×2。

## 006 Figma 导出图标把示例文字转曲烘进 SVG
- **现象：** 文件夹卡片在 UI 上显示两组标题——动态渲染的标题之上还有一组固定的"新建文件夹 / 132 个子文件夹 / 1,321 个文件"。
- **原因：** `folder-card*.svg` 从 Figma 导出时，设计稿里的示例文字被转曲成 path 一并导出（viewBox 193×204 中含 42px 文字区）。
- **解法：** 剔除起始 y ≥ 160 的文字 path，viewBox 裁为 193×162 纯图标区；卡片标题/数量由组件动态渲染。
- **预防：** 图标类 SVG 导出前删除设计稿文字（或仅导出图标图层）；新增图标入库时检查 viewBox 与 path 数是否异常。

## 005 超大列表原生滚动拖拽必然闪白（棋盘格）

- **现象：** 10 万条列表拖拽原生滚动条，起步必闪一帧空白；加大 buffer、增量渲染、wheel 预渲染、同步渲染均只能缓解。
- **原因：** 浏览器对滚动条拖拽是合成器先行——拖块 1px 对应内容瞬移上千 px，主线程收到 scroll 事件时浏览器已画完一帧空白；且超大列表瞬移无 buffer 可覆盖（棋盘格）。
- **解法：** 自定义滚动——禁止原生滚动，wheel / 拖拽 / 键盘事件里先渲染目标区域、再用 transform 挪动画布，同一 JS 任务同一帧原子提交。实测完全不闪烁。
- **预防：** 主列表（内容展示区）滚动采用自定义 transform 方案，阶段 1 实现主窗口网格时直接沿用（原型见 `src/proto.ts`）。

## 004 OLE 拖拽放线程池导致无声失败

- **现象：** `drag::start_drag` 返回成功、状态显示"拖拽结束"，但目标位置没有文件。
- **原因：** 命令写成 async，被调度到线程池；Windows OLE 拖拽（DoDragDrop）必须在拥有窗口的主线程发起，线程池里拖拽被瞬间取消且无报错。
- **解法：** 改为同步命令（Tauri 同步命令运行于主线程），拖拽模态循环本身就是消息泵，实测拖出成功。
- **预防：** OLE / COM / 窗口消息类调用（拖拽、剪贴板、Shell）默认放主线程执行；确需后台执行时必须先验证行为。

## 002 `tauri dev` 一直 Waiting for frontend dev server

- **现象：** vite 显示 ready，Tauri 却反复 "Waiting for your frontend dev server to start"。
- **原因：** vite 默认把 dev server 绑到 IPv6 的 `::1`，而 Tauri 按 `127.0.0.1` 探测，localhost 解析不一致。
- **解法：** vite.config.ts 显式 `server.host = "127.0.0.1"` + `strictPort`，tauri.conf.json 的 devUrl 同步改为 `http://127.0.0.1:5173`。
- **预防：** 该项目配置已固化在 vite.config.ts / tauri.conf.json，新机器克隆即用。

## 003 vite watcher 监视 cargo 产物导致 EBUSY 崩溃

- **现象：** `tauri dev` 启动后 vite 崩溃：`Error: EBUSY: resource busy or locked, watch '.../src-tauri/target/debug/deps/app_lib.dll'`。
- **原因：** vite 的文件监视默认覆盖项目根目录，cargo 构建时改写并锁定 `src-tauri/target/**` 下的 dll，watcher 报错后杀死了 beforeDevCommand。
- **解法：** vite.config.ts 增加 `server.watch.ignored = ["**/src-tauri/**"]`。
- **预防：** 同上，配置已固化；新增前端目录时注意 watcher 排除范围。

## 001 PySide6 快速滚动卡顿（历史项目）

- **现象：** 虚拟缓存、懒加载都上了，快速拉动滚动条仍卡顿。
- **原因：** 疑为 QWidget 体系 CPU 光栅 + Python 侧绘制委托 + 滚动时同步解码/IO，并非单纯"没走 GPU"。
- **解法：** 本项目改用 Web 技术栈（浏览器合成器 GPU 加速，createImageBitmap 离线程解码）。
- **预防：** 已写入 01_开发规范 第 7 条——列表虚拟化、异步解码、布局预计算（用 metadata 宽高）、滚动降级（主色占位）。验收线：10 万资源快拖不掉帧。

## 038 ffmpeg-next 与 ffmpeg 头文件版本漂移：bindgen 现场生成，crate feature 门槛表滞后于滚动 master

- **现象：** 2026-08-20 阶段四 spike，ffmpeg-next 8.1.0 配 BtbN 最新 master dev 库（avcodec 63 = 9.0-dev）编译 15 错（`AV_PKT_DATA_DYNAMIC_HDR_SMPTE_2094_APP5` 等枚举未覆盖）；换 autobuild-2025-08-31 库（avcodec 62.13，ffmpeg 8.0 时期）后仍 1 错：`AV_FRAME_DATA_EXIF not covered`。
- **原因：** ffmpeg-sys-next 是 **bindgen 按本机头文件现场生成绑定**——头文件里的新枚举值会出现在生成代码里，而 ffmpeg-next 高层代码的 match 臂由 `ffmpeg_X_Y` feature 门控，feature 又按**版本号门槛表**（如 `("ffmpeg_8_1", 62, 28)` = avcodec major 62 且 minor ≥ 28）探测。EXIF frame side data 实际在 avcodec 62.13 已合入，crate 作者按 62.28 写的门槛 → bindgen 产物含枚举、高层 match 缺臂，E0004。
- **解法：** 两步——① 按 crate 同期挑 dev 库（BtbN 无版本化 tag，只有 master 滚动 + 月末 autobuild：autobuild-2025-08-31 即 ffmpeg 8.0 发布后 9 天）；② 残余个别枚举用 `[patch.crates-io]` 本地副本（`patches/ffmpeg-next`），仅把 `src/util/frame/side_data.rs` 三处 cfg `ffmpeg_8_1`→`ffmpeg_8_0`（其余 8_1 门控项在本头文件不存在，保持原样）；patch 副本须删 `.cargo-checksum.json`。
- **预防：** 用 bindgen 系 crate（ffmpeg-next、*-sys）时，dev 库版本不是越新越好——与 crate 发布同期对齐；`AVFrameSideDataType`/`AVPacketSideDataType` 这类增长型枚举是漂移高发区。铺量进主线时该补丁随依赖一起固化，升 crate 先全量编译看漂移面。

## 039 BtbN lgpl 构建 libwebp 只开 encoder：动图 webp 在 ffmpeg 管线无解

- **现象：** 2026-08-20 spike 实测 animated webp 解码失败：`webp_pipe` demuxer probe 报 `skipping unsupported chunk: ANIM/ANMF`、`Could not find codec parameters`；`find_by_name("libwebp_anim")` / `("libwebp")` 均 None。
- **原因：** 两层。① BtbN lgpl 构建 `--enable-libwebp` 只注册了 **encoder**（主线 sidecar 转 animated webp 用的就是它），libwebp / libwebp_anim **decoder 均缺席**；② ffmpeg 原生 webp decoder 本身不支持动画（ANIM/ANMF chunk 直接跳过，找不到静态图像数据即败），demuxer 层面就过不去——与 decoder 选型无关。
- **解法：** 动图 webp 不进 ffmpeg 管线，归主线既有 **image-webp** 纯 Rust 解码（`services/anim.rs` 生产在跑，逐帧 + delay 全量具备）；ffmpeg 管线管 GIF / 视频 / 其余格式。不为此换 GPL 构建（gyan full 含 libwebp decoder 但 GPL 传染）。
- **预防：** 评估"某格式能否进 ffmpeg 管线"要查三项：demuxer 支持、decoder 注册（`--list` 探针先跑）、构建 config（BtbN lgpl ≠ gyan full 的编码器清单）；sidecar 能**编码**不代表能**解码**。

## 040 Windows std::thread::sleep 粒度 15.6ms：30fps 帧节奏顶不满（实测 25.6）

- **现象：** 2026-08-20 spike 壳 pace=1 原速播放实测：50 路 H264（30fps 源）每路稳态仅 25.6fps；50 路 GIF（10fps 源，100ms/帧）每路 9.1fps 接近顶满。
- **原因：** Windows 默认定时器分辨率 15.6ms——`sleep(33ms)` 实际睡到 ~48ms（向上取整到粒度倍数），30fps 节奏天然顶不满；100ms 睡眠只 +15% 偏差，动图场景影响小。
- **解法：** spike 阶段不处理（25.6fps 卡片预览已流畅，CPU 29% 数据有效）；铺量两路——① `timeBeginPeriod(1)` 提定时器精度（进程级，退出配 timeEndPeriod）；② 更优：节奏权交消费端——后端全速/半速解码、帧槽恒持最新帧，前端 rAF 节奏取帧渲染（天然 60Hz 对齐、无睡眠精度问题，帧槽模型 spike 已验证）。
- **预防：** Windows 上做帧调度/节流，凡 sleep < 50ms 都要想到 15.6ms 粒度；高精度场景优先"生产者全速 + 消费者节奏"模型，别让生产者睡。

## 037 异步 watch 窗口期旧布局越界：Vue 渲染管道被异常打"半死"——点了有反应（store 变）但 DOM 不更新

- **现象：** 2026-08-19 用户实机：分组/删组操作多了后 UI"卡死"——目录树选中态取消不掉、递归显示开关点不动；不是主线程忙（无长任务），而是**点击照常生效（store 状态变）、界面却不重渲染**，越操作越坏。
- **原因：** useGridLayout 的 `items`/`sections` watch 是异步 flush——items 已变短（切视图/归组变化）而 boxes/rows 还是上一轮旧布局的窗口期里，`visibleCards` 用 `items[旧box.i]` 取到 `undefined`，模板 key 求值 `c.asset.assetId` 抛 TypeError → Vue 更新队列中断并被污染（连锁 `shouldUpdateComponent` 读 null 的 `emitsOptions`——已卸载组件仍被 patch）。渲染管道一旦被打断，后续每次操作继续抛错，DOM 永久落后状态——用户观感即"卡死"。CDP 混合压力探针（24 轮：弹窗增删/菜单删组/折叠+树切换/滚动+悬停轮转）稳定复现：R17 起异常连发、递归开关切换后卡片数不跟随（与用户症状同构）；headless 桩环境即可现，与后端/缩略图无关。
- **解法：** 两处窗口期防御——`visibleCards` 跳过 `undefined` asset、`anchorKey` 取不到卡就不锚定（旧布局在 items 变化后本就该等 relayout 一致化，跳过是唯一正确语义）。修后同探针 24 轮零异常、递归开关联动恢复。
- **预防：** "items 与布局结果（boxes/rows）来自两个响应式源、靠异步 watch 一致化"的手写虚拟滚动/布局结构，**一切交叉索引读都按可能越界写**（`items[box.i]` 必须先判存在）。症状为"界面点了没反应但进程不崩"时，先查渲染管道是否被未捕获异常打半死（Console 红字 / exceptionThrown），再怀疑事件监听泄漏或主线程卡死。

## 036 描边颜色过渡 = 重绘型动画：GPU 合成损伤区漏覆盖，取消状态后品牌色像素残留

- **现象：** 卡片 / 输入框在聚焦、选中、右键选中再取消后，圆角处（徽标角上）残留几个品牌色像素点；用户实机从开发至今反复出现，headless 软渲染探针 30 轮复现不了（残留是 GPU 合成路径 artifact）。
- **原因：** `border-color` / `box-shadow` 的 transition 是**重绘型动画**——过渡每帧光栅重绘，圆角 + 1.5px 分数物理像素的抗锯齿边缘在动画结束时，合成器损伤区（damage rect）偶发没覆盖全部受影响像素，上一态的品牌色像素留在屏幕上。
- **解法：** 状态描边改**双（伪元素）层结构**——常态层（如 1px 暗框 / 透明框）无过渡恒在；状态层（1.5px 品牌色边框）`opacity 0↔1` 过渡（合成器属性，无光栅重绘）；hover↔选中换色瞬时切。落地：AssetCard / FolderCard / ArchiveCard / InboxDiskSection / PreviewFrameStrip 伪元素层；AppInput 统一壳化（原"非 clearable 裸 input"分支废除——input 无伪元素；CreateLibraryModal 的 `$el.focus()` 改 expose `focus()`）+ AppSearchBar ::after。
- **预防：** **状态描边（hover / 选中 / 聚焦的边框）一律 opacity 过渡**，禁 border-color / box-shadow 颜色过渡（速查表 §7 已收录）；写描边动画先想"它是重绘型还是合成器型"。验证残留要靠非 headless（GPU）路径探针（cdp-border-residue-probe.py `--window`），软渲染复现不了不等于不存在。

## 030 状态切换用 v-if 摘挂内容：空 flex 容器基线漂移，弹窗整体跳 1px

- **现象：** 复选框勾选 / 取消时，所在弹窗全部内容（标题、按钮）微微上移 / 下移 1px，像窗口抖了一下；删除资源库确认窗的"同时删除素材文件"复选框必现。
- **原因：** 对勾图标用 `v-if` 摘挂——未选中时 `.box` 从"有内容的 flex 容器"变"空 flex 容器"，CSS 基线推导规则不同（空 flex 容器基线 = 底缘，有内容 = 内容基线），按钮在 `.desc` 行盒中的占位高度差出 1px，模态框垂直居中重排，全内容跟着跳。视频帧逐像素比对实证：未选中帧 = 选中帧整体上移 1px（dy=-1 完全重合）。讽刺的是组件注释本就写着"对勾透明度过渡"，`v-if` 让这条 transition 从未生效。
- **解法：** 对勾常驻 DOM，`:class="{ off: !model }"` 切 opacity——两态 DOM 结构完全一致，布局与基线零变化。
- **预防：** **状态切换只改样式、不摘挂 DOM**——凡 `v-if` 用在"纯显隐、占位固定"的装饰性元素上（图标 / 角标 / 对勾），都要警惕它同时改变了父容器的基线 / 尺寸推导；显隐用 opacity / visibility / transform。检查方法：切换状态前后各取一次 `getBoundingClientRect()` 比对，任何像素差都是布局抖动。

## 028 `:hover:not()` 伪类计入特异性：悬停规则压过状态类，拖拽并入只见边框不见填充

- **现象：** 树 item 拖拽并入（drop-into）时 1.5px 品牌色边框正常，30% 品牌填充完全看不见，像没加一样；文件夹卡片同口径填充正常。
- **原因：** hover 规则 `.tree-item.child:hover:not(.selected)` 的特异性——`:hover` 与 `:not(.selected)` 都按类级计入（`:not()` 取其参数），合计 (0,4,0)，压过 `.tree-item.child.drop-into` 的 (0,3,0)；拖拽时鼠标正悬停在目标 item 上，hover 的暗-悬停罩层把并入的 30% 品牌罩层整个盖住。box-shadow 无 hover 规则竞争所以边框正常。
- **解法：** 三条 hover 规则补 `:not(.drop-into)`——状态类（选中 / 并入）存在时 hover 罩层退让（与既有 `:not(.selected)` 同思路）。
- **预防：** 写 `:hover:not(X)` 规则时，**把它当成比双类更高的特异性来源**——凡后续新增"悬停期间也要显示的状态类"（选中 / 拖拽 / 高亮），都要回头检查 hover 规则是否会把它的 background 压掉；状态类与 hover 共存时优先用 `:not(状态)` 排除法，而不是指望堆高状态类特异性。

## 027 裸 tsc 不检查 .vue：SFC 自由变量 ReferenceError 全绿漏网

- **现象：** 给 AssetGrid 加激活闸时引用了只存在于 ContentArea 的 `active` 变量，`pnpm tsc --noEmit` 与 `pnpm build` 双双全绿；运行时空格预览彻底失效（每次按键监听器内抛 ReferenceError）。
- **原因：** `pnpm tsc` 调的是裸 `tsc`——只检查 `.ts/.tsx`，**`.vue` 文件的 script setup 完全不查**；vite/rolldown 编译 SFC 只做转译不做类型检查。于是 .vue 里的未定义变量、类型错误在"tsc / build 全绿"下全部漏网，只能运行时暴露。
- **解法：** 本例修复 = 激活态由 ContentArea 以 `panelActive` prop 显式传给 AssetGrid（AssetGrid 拿不到 panelApi / panel id）。
- **预防：** ① 跨组件搬代码时警惕"目标文件没有该变量"——.vue 没有编译器兜底；② **"tsc/build 全绿"不等于 .vue 无类型错**，SFC 关键改动（尤其新引用变量）要在 dev 里实际点一遍对应交互；③ 待评估引入 `vue-tsc` 补盲（记 09 待办，涉及依赖与脚本变更）。

## 026 系统级指针抢夺：pointerup / pointercancel 双丢，手势视觉层永久残留

- **现象：** 框选进行中按系统截图（或第三方截图工具）、以及框选拖到屏幕边缘触发 Win11 snap 分屏预览后，框选矩形永远盖在界面上不消失；UI 不卡死、可继续操作，但矩形一直在。
- **原因：** 框选手势的清除完全依赖 viewport 的 `pointerup` / `pointercancel`（setPointerCapture 定向送达）；系统截图工具抢焦点、snap 预览/窗口 System Move 抢指针时，这两个事件**双双不送达**——手势状态机永远停在"拖拽中"，marquee 矩形无人清除。
- **解法：** 两道兜底强制取消（`useMarquee.forceCancel`）：① viewport 监听 **lostpointercapture**——capture 被系统剥夺时的对症事件（不伴随 up/cancel 的场景全靠它）；② `window blur`——截图工具抢焦点场景。拖拽引擎（dragOperation）同根：begin 时挂 `window blur → endDrag(true)` 取消兜底，防 ghost / 落点指示同类残留。
- **预防：** 任何"按下-移动-松开"三段式手势（框选 / 拖拽 / scrub），结束条件不能只挂 pointerup/pointercancel——系统层随时可能抢指针（截图、snap、系统级窗口移动、远程桌面），**lostpointercapture + window blur 双兜底是标配**；WebView2/Chromium 对 capture 丢失不发 cancel 没有跨平台保证。

## 025 dockview 自动布局回调持旧尺寸：同帧 forceLayout 被覆盖，网格渲染宽恒晚一帧

- **现象：** 侧栏收展动画过程中：① 顶栏（标签栏 46 C3）右端断开，露出 dock 宿主 C1；② 中间面板右缘锚点失效——收左栏时右缘应钉死不动，实际整个网格（含滚动条）被往左拽、动画结束再回弹；③ 收展末尾因重排闪烁一帧。三现象同根。
- **原因：** App.vue 的收展驱动在同一 rAF 回调里写完侧栏宽度后 `forceLayout(当前宽)` 灌给 dockview——但 dockview 自身的自动布局走 `ResizeObserver → requestAnimationFrame`（dockview-core `dom.ts watchElementResize`），回调注册在同一帧的 rAF 队列里且**排在我们之后、携带的是触发时的旧尺寸**：我们先灌当前宽，它紧随其后把网格宽度覆盖回上一帧。CDP 逐帧实测：网格渲染宽恒等于 dock 宿主**上一帧**宽，滞后最多 ~75px。
- **解法：** 灌宽时机从 rAF 阶段改到 **ResizeObserver 阶段**——App.vue 挂 `dockResizeObs` 监听 dock 宿主，RO 回调在当帧全部 rAF 之后、绘制之前执行，此刻读到的就是当帧最终宽，`tabs.forceLayout` 同步写网格；dockview 的陈旧回调此前已执行完毕，再也覆盖不到。侧栏收展、窗口拖改尺寸统一走此路径。逐帧复测：每一帧 `dockHost == grid == tabs` 精确到 0.1px，收左栏时网格右缘恒定钉在窗口右缘。
- **预防：** 与第三方组件库做"逐帧尺寸同步"时，先搞清对方自动布局的事件源与时机（RO / rAF / 微任务），在**比它更晚、仍在绘制前**的时机同步（RO 阶段是浏览器渲染流水线里绘制前最后一站）；同帧内后执行的旧尺寸回调会覆盖先执行的同步写入——顺序错误时"同步灌值"形同虚设。排查这类逐帧问题用 CDP 劫持 rAF 逐帧步进 + `getBoundingClientRect` 探针，比截图猜因快得多。

## 024 dockview-vue 多根 Fragment + 父级 scoped 尺寸失效：dock 区域全黑且无报错

- **现象：** 接入 dockview 后中间面板全黑（连标签栏 DOM 都"看不见"），控制台**没有任何报错**——组件全部正常创建，纯属 CSS 事故（同类事故见 021）。
- **原因：** DockHost 里给 `<DockviewVue class="dock-root">` 配 scoped 样式 `.dock-root { height: 100% }`。DockviewVue 渲染为 **Fragment 多根**（容器 div + portals 组件），父组件的 `data-v-*` scope id 不会自动落到多根组件的任何节点——scoped 规则匹配失败，容器高度为 0，`api.layout(w, 0)` 后全部内部元素绝对定位在 0 高容器里 = 全黑。
- **解法：** 尺寸规则改 `:deep(.dock-root) { width/height: 100% }` 穿透。
- **预防：** 给**第三方多根组件**传 class 配尺寸/布局样式时一律 `:deep()`（或全局样式表）；单根组件根元素才继承父 scope id。"无报错但不显示"先量 `getBoundingClientRect()` 再怀疑 JS。

## 023 dockview-vue 的 props 传递约定：整组包在一个 `params` prop 里

- **现象：** 自定义 panel / tab / header-actions 组件报 `Missing required prop: "api"`、setup 里读 `api.isActive` 抛 TypeError。
- **原因：** dockview 类型定义给人的直觉是 Vue 组件按字段收 props（`api` / `containerApi` / `params`…），但 dockview-vue v7 源码（`VueRenderer.init`）实际把整组 framework props **包进名为 `params` 的单一 prop**：组件收到的是 `{ params: { params: 用户参数, api, containerApi, tabLocation } }`；`updateParameters` 后该对象整体换新（响应式跟随）。文档未写明这一点。
- **解法：** `defineProps<{ params: Record<string, unknown> }>()`（字面量声明绕开 rolldown 无法解析 node_modules 类型的限制）+ 使用处断言回 `IDockviewPanelProps` 等类型；读用户参数用 `props.params.params.viewKey`。
- **预防：** 用 dockview-vue 自定义任何渲染器（panel / tab / header actions / watermark）都按"`params` 单 prop 包裹"约定接；第三方库 props 行为以源码为准、类型定义只作参考。

## 022 窗口几何持久化把"最小化态"写回：启动恢复成一小块

- **现象：** 软件窗口只剩一小块（422×313 甚至更小），重启也恢复不回去。
- **原因：** Windows 最小化窗口报告坐标 (-32000,-32000) 与退化尺寸（实测 237×39）；窗口几何持久化（resize/move 防抖写回 config settings.window）未做任何守卫，最小化 / 隐藏托盘途中的 onMoved/onResized 把坏值写进配置，启动恢复即成小窗（恢复侧下限 400×300 形同虚设）。
- **解法：** 写回三道守卫——isMinimized 不写、尺寸 <800×500 不写、坐标 <-10000 不写；恢复下限提为 800×500；用户 config 里的坏几何直接移除（恢复默认尺寸居中）。
- **预防：** 一切持久化"系统可能给出退化值"的状态（窗口几何 / 显示器拓扑 / 输入设备），写入前必须校验合理性（最小尺寸 / 坐标域 / 枚举白名单），恢复侧再兜一层 clamp——写、读两端都不可信。

## 021 Vue SFC scoped 块内 `:global(x)` 带后代选择器被吞：拖拽时整窗黑屏

- **现象：** 拖拽卡片一开始整个窗口全黑（只剩窗口边框），松手立即恢复——像渲染崩溃，实为 CSS 事故。
- **原因：** AssetCard scoped 样式块内写 `:global(body.dragging) .thumb .actions { opacity: 0 }`，**SFC scoped 编译把 `:global()` 后面的后代选择器吞掉**，产物只剩 `body.dragging{opacity:0;pointer-events:none}`（dist CSS 实证）。拖拽开始 body 加 dragging 类 → 整个 body 透明度归零、只剩窗口底色 = 全黑，松手移除类即恢复。
- **解法：** 全局规则改写到独立的非 scoped `<style>` 块（`body.dragging .asset-card .thumb .actions`）——类名在 scoped 编译产物中原样保留可正常匹配；特异性算足（(0,4,1) 压过 `.asset-card:hover .actions` (0,4,0)），构建后 grep dist CSS 验证产物。
- **预防：** scoped 块内 `:global(...)` 必须整包完整选择器、不能带后代；要影响全局（body 类切换等）一律写非 scoped 块或全局样式表；写这类"看不见"的规则（opacity / visibility / display）后 grep 一次 dist CSS 确认编译产物没变形。

## 020 vite 起不来：listen EACCES——端口被 Windows NAT 动态保留段覆盖

- **现象：** `pnpm tauri dev` 失败：`beforeDevCommand terminated with non-zero status`；手动 `pnpm dev` 报 `Error: listen EACCES: permission denied 127.0.0.1:5173`——不是 EADDRINUSE（无进程占用 5173），昨天还能正常 dev。
- **原因：** Windows NAT（Hyper-V / WSL / Docker 的 winnat 服务）会动态保留 TCP 端口段，`netsh interface ipv4 show excludedportrange protocol=tcp` 可见 5173 落在 5144-5243 保留段内；保留段随系统重启 / winnat 重启漂移，所以"昨天好的今天不行"。
- **解法：** 换保留段外端口：vite.config.ts `server.port` 5173 → **5373** + tauri.conf.json `devUrl` 同步（两文件必须一起改，否则 Tauri 一直 Waiting for frontend dev server，同踩坑 002 的联动）。
- **预防：** dev 报 EACCES（非 EADDRINUSE）先查 excludedportrange 再查占用；端口变更必须 vite.config.ts 与 tauri.conf.json 同步；若保留段漂移再次覆盖 5373，同法再换（也可用 `net stop winnat` 重置保留段，需管理员且重启后可能复发，不作首选）。

## 019 增量链接缓存损坏：LNK2019 "无法解析的外部符号 anon…" 挡住 dev 启动

- **现象：** `cargo test` / `pnpm tauri dev` 编译末期链接失败：`error LNK2019: 无法解析的外部符号 anon.{hash}.llvm.{hash}`（serde Serialize/Deserialize 等泛型符号），报 N 个无法解析后 `fatal error LNK1120`、`could not compile 'app' (lib)`；代码本身无任何问题，且错误符号与本次改动无关。
- **原因：** Rust 增量编译的代码生成单元缓存（`target/debug/incremental/`）与前一次编译状态不一致（本机 2026-07-28 一天内出现 2 次；opt-level=1 的 dev profile + cdylib 组合下偶发）。
- **解法：** `rm -rf src-tauri/target/debug/incremental` 后重跑即可（只清增量缓存，依赖与 crate 产物保留，重编约 1 分钟）；不要 `cargo clean`（全量重编 10 分钟级）。
- **预防：** 遇到"符号与改动无关"的 LNK2019 先清 incremental 再怀疑代码；若日后频繁复发，再考虑 `[profile.dev] incremental = false`（代价是每次改代码重编 app crate 从秒级变分钟级，暂不关）。

## 018 LGPL ffmpeg 构建没有 libx264：转码静默失败

- **现象：** 导入 mov 后预览报"该格式暂时无法播放"，转码兜底没生效；手动跑 sidecar 才发现 `libx264` 编码器不存在。
- **原因：** 5.1 选型特意用 BtbN **LGPL** 静态构建（避免 GPL 传染），而 x264 正是 GPL 许可——LGPL 构建不含 libx264。写转码参数时按惯性填了 `-c:v libx264`，ffmpeg 因编码器缺失非零退出。
- **解法：** 改用 LGPL 构建内可用的 h264 软编码器 `libopenh264`（Cisco，BSD 许可，无传染）——注意它不支持 x264 的 crf/preset，用 `-b:v` 码率控制；`-encoders` 列表核对过 libvpx-vp9 / 硬件编码器（h264_mf / nvenc / qsv）也在但前者太慢后者依赖机器，不作首选。
- **预防：** 给 sidecar 写编解码参数前，先用 `-encoders` / `-decoders` 核实该构建实际带了什么；许可选型（LGPL）与功能清单是一体的，改构建变体时必须重核。

## 017 dev 构建性能误判：慢的是 O0 不是管线

- **现象：** dev 模式（`pnpm tauri dev`，cargo debug 构建）下动图帧条 18 帧要 5-10 秒、CPU 风扇猛转；序列帧 17 张"秒读"。排查方向一度以为是架构问题（帧条反复解析 GIF / 等解包 / 大图二次解码）。
- **原因：** 纯 debug（opt-level 0）的图像解码 / 重采样比 release 慢 10-30 倍，基准实测 1080p webp 帧条 O0 = 725ms/帧 vs release = 43ms。两层叠加：① 依赖 crate 内的解码（webp 解码 455ms）；② **泛型函数在调用方单态化**——imageops::resize 的代码生成在我们 crate（O0）而非 image crate，只给依赖开优化管不到它（261ms）。序列帧"秒读"只是因为 PNG 小图基数小。
- **解法：** Cargo.toml `[profile.dev] opt-level = 1`（管泛型单态化）+ `[profile.dev.package."*"] opt-level = 2`（管依赖内部代码），效果 725→57ms/帧，与 release 同量级；依赖只编一次，日常增量构建不受影响。
- **预防：** dev 模式下任何"慢"的结论先隔离构建配置变量——性能判定以 release（或 O2 基准）为准，优化需求先在 release 复测再立项；dev 优化配置已固化 Cargo.toml（图像基准 thumbnail.rs bench_frame_strip_stages #[ignore] 可复跑）。

## 016 GIF 元数据探测用解码级遍历：导入大 GIF 卡数秒

- **现象：** 导入一个几十 MB 的 GIF 要等好几秒才出卡片，小图却无感。
- **原因：** `anim::probe_gif` 用 image crate `into_frames()` 逐帧**解码像素**来数帧数、累加时长——GIF 格式没有全局帧数头，要数帧必须遍历整个文件，而 image crate 只提供解码级遍历，探测成本 = 完整解码一遍。
- **解法：** 改纯字节级扫描（scan_gif）：按 GIF 块结构跳块——0x2C 图像描述块数帧、0xF9 图形控制扩展拿 delay 累加时长、色表与 LZW 子块链按长度跳过，只读字节不解码；与 image crate 解码结果做交叉校验单测防解析偏差。探测从"解码一遍"降为"读一遍"，导入零等待。
- **预防：** 格式探测（probe）只允许"读一遍文件"量级的开销，禁止解码级操作；帧数/时长确实要遍历才能拿到的格式，用字节级块扫描，把解码留给真正需要像素的环节（缩略图 / 解包）。

## 015 视觉类目检用合成样本：口径缺陷被掩盖

- **现象：** 音频波形渲染迭代十几轮，用 ffmpeg 合成的 8 秒噪声样本目检一直"通过"，用户真实 3 秒配音文件却整体发淡、峰值无辨识度。
- **原因：** 渐变叠加机制的效果强依赖"文件时长 / 窗口数"比例——长文件每窗口样本多、纵线长且重叠，合成样本看着正常；用户短文件每窗口仅 ~2 样本，纵线短且散，叠不出实心主体。合成样本的统计特性与真实素材完全不同。
- **解法：** 取用户参考版音频本体跑候选算法**逐像素比对**（`tools/waveform-match.py`），匹配度 95%+ 才定稿；不再凭合成样本目检下结论。
- **预防：** 视觉 / 渲染类功能验收，样本必须用用户真实文件（覆盖最短 / 最长 / 最静 / 最响两端），合成样本只能做逻辑单测，不能做观感目检（呼应 012 "新格式接入先用用户真实样本验证"）。

## 014 测试 exe 链接 tauri GUI 依赖链：0xc0000139 入口点未找到

- **现象：** preview_queue 测试持有 `AppHandle` 后，Windows 上测试 exe 加载即失败（STATUS_ENTRYPOINT_NOT_FOUND），全部测试无法启动。
- **原因：** 测试代码经 `AppHandle::emit` / 析构把 tauri GUI 依赖链（rfd 的 `comctl32!TaskDialogIndirect` 等）拉进测试 exe，而测试 exe 无 comctl32 v6 清单（tauri-build 只给主程序内嵌），System32 的 v5.82 无此导出。build.rs `/MANIFESTINPUT` 与 tauri-build 清单资源冲突、`#[link(+whole-archive)]` LNK1356，均不可行。
- **解法：** AppHandle 字段与 emit 实现 `#[cfg(not(test))]`，测试构建起无事件实例（`start(None)`，句柄 mem::forget 丢弃）——生产路径行为不变。

## 013 Tauri v2 非 async 命令在主线程执行——主线程内 build 窗口死锁

- **现象：** 预览"新窗口打开"点击后整个进程卡死——主窗口无法拖动/关闭、托盘菜单无响应；新窗口出现但不渲染内容、压在主窗口下方。
- **原因：** Tauri v2 中**未声明 async 的命令在主线程执行**。`open_preview_window` 是 sync 命令，在主线程内 `WebviewWindowBuilder::build()`，窗口创建流程与主线程事件循环互等，主线程死锁。
- **解法：** 命令改 `pub async fn`（线程池执行，build 内部 dispatch 回主线程不阻塞——官方 multiwindow 示例路径）；preview 模块 5 条命令一并 async 化（list_sequence_frames 帧条小图生成等 IO 重活也不该占主线程）。
- **预防：** Tauri v2 命令默认主线程执行——**凡涉及窗口创建 / IO 重活 / COM 调用的命令一律 async**；纯内存快操作（取锁读索引）才用 sync。新增命令时对照本条自查。

## 012 PSB 结构判定看签名（8BPB）而非版本号

- **现象：** 公司工具链导出的 PSB 素材（879×1016）导入后无预览，回退成系统图标；宽高探测正常。
- **原因：** 该文件是 **8BPS 签名 + version=2** 的变体（规范本意 8BPS+1=PSD、8BPB+2=PSB，现实存在交叉）。代码按签名判定非 PSB，把 Layer & Mask 节的 8 字节长度字段误读为 4 字节，seek 错位后 compression 读到垃圾，解码失败。
- **解法：** PSB 结构判定改看**版本号**（version=2 → 8 字节长度字段），签名 8BPS/8BPB 均可；.psd 解码失败也兜底走 PSB 解析（反向变体同理）。
- **预防：** 解析二进制格式时，结构变体以"版本号 / 魔数 + 实测"为准，不轻信规范的组合枚举；新格式接入先用用户真实样本验证（构造数据测不出变体）。

## 010 `mod core` 遮蔽内建 core crate

- **现象：** 数据层新增 `mod core;` 后编译报错：`core::ffi::c_void` 解析失败（cannot find `ffi` in `core`）。

## 008 Figma 描边 inside 不占空间，CSS border 外扩占位

- **现象：** 按 Figma 标注的 padding 实现后，所有带边框容器的视觉间距都比设计稿宽 1~2px（如主窗口 padding 6 看着像 8）。
- **原因：** Figma 描边（stroke）默认 inside 对齐、不占布局空间，标注 padding 6 中有 2px 被描边占用；CSS `border` 在 padding 之外另占空间，`border 2px + padding 6px` 视觉就是 8px。每个带边框容器都差一个边框厚度。
- **解法：** 组件线条一律用 `box-shadow: inset 0 0 0 {宽}px {色}` 模拟（不占布局空间，与 Figma inside 描边逐像素一致）；hover/选中换色改 shadow 即可，还省掉了"透明边框占位防抖动"的 hack。
- **预防：** 已写入 `01_开发规范` 第 4 条——UI 组件禁止用 `border` 画设计线条，统一 inset box-shadow（真正分隔内容用的分割线另议）。

## 007 无边框窗口装饰四轮探索，终局为不透明 + 原生 DWM

- **现象：** 无边框窗口要阴影 / 圆角 / 1px 线框 / resize 判定，四轮方案全部翻过车：① window-shadows crate（1px 直角线框 + rwh 版本分裂）；② tauri `shadow: true` + DWM 抑制（主题边框 / DWM 圆角 / 顶边线 / 圆角外底色块，抑制不尽）；③ 全透明 + CSS 圆角阴影（当时判为终局）；④ 原生方案。
- **方案③ 同样翻车（用户实测四宗罪）：** inset 线框被三栏贴边背景遮住看不见；resize 判定双区域（阴影边缘 + 窗口边缘）；blur 40 超出 20px 阴影带被物理边缘裁成硬边；阴影带 20px 无法穿透点击到下层软件。
- **终局解法：** `transparent: false` + `shadow: true`（tao undecorated shadow）——Win11 DWM 圆角 8px 恰与设计一致、DWM 原生阴影（无硬边无阴影带）、resize 判定统一在物理 = 可视边缘（tao 只给顶边，四边用 `startResizeDragging` 热区补足）；mac 系统圆角 + 系统阴影；Win10 直角接受；线框用 `DWMWA_BORDER_COLOR` ≈ C4-15 合成色（Win11+）。
- **预防：** 桌面应用的窗口装饰（圆角 / 阴影 / 边框）优先用系统原生能力并按平台接受差异（Win11 8px / mac 系统 / Win10 直角），不要为追求跨平台像素一致去自绘——透明分层窗口与 DWM 的交互全是边角问题。

## 006 Figma 导出图标把示例文字转曲烘进 SVG
- **现象：** 文件夹卡片在 UI 上显示两组标题——动态渲染的标题之上还有一组固定的"新建文件夹 / 132 个子文件夹 / 1,321 个文件"。
- **原因：** `folder-card*.svg` 从 Figma 导出时，设计稿里的示例文字被转曲成 path 一并导出（viewBox 193×204 中含 42px 文字区）。
- **解法：** 剔除起始 y ≥ 160 的文字 path，viewBox 裁为 193×162 纯图标区；卡片标题/数量由组件动态渲染。

## 005 超大列表原生滚动拖拽必然闪白（棋盘格）

- **现象：** 10 万条列表拖拽原生滚动条，起步必闪一帧空白；加大 buffer、增量渲染、wheel 预渲染、同步渲染均只能缓解。
- **原因：** 浏览器对滚动条拖拽是合成器先行——拖块 1px 对应内容瞬移上千 px，主线程收到 scroll 事件时浏览器已画完一帧空白；且超大列表瞬移无 buffer 可覆盖（棋盘格）。
- **解法：** 自定义滚动——禁止原生滚动，wheel / 拖拽 / 键盘事件里先渲染目标区域、再用 transform 挪动画布，同一 JS 任务同一帧原子提交。实测完全不闪烁。
- **预防：** 主列表（内容展示区）滚动采用自定义 transform 方案，阶段 1 实现主窗口网格时直接沿用（原型见 `src/proto.ts`）。

## 004 OLE 拖拽放线程池导致无声失败

- **现象：** `drag::start_drag` 返回成功、状态显示"拖拽结束"，但目标位置没有文件。

## 031 serde 内部 tag 枚举：`rename_all` 只改变体名，不改字段名

- **现象：** 2026-08-13 扫描重复文件"当前目录"实机报错 `invalid args 'scope': missing field 'folder_id'`——前端发 `folderId`，后端却在等 `folder_id`。

- **预防：** 给 Tauri 命令写枚举参数时，凡带字段的 struct 变体一律 `rename_all` + `rename_all_fields` 成对写，并配一条 JSON 反序列化断言；不要靠字段级 rename 补丁（新变体必漏）。

## 032 拖拽僵尸会话：无 pointer capture 丢 pointerup，旧 sess 被静默复用吞 click

- **现象：** 2026-08-13 用户多次实机遇到"文件树 / 快速访问 item 点不动（卡死），非要双击才能选中；快速访问与目录树 item 同时带选中态"——间歇出现、莫名其妙，每次重启解决（内存态损坏特征）。
- **原因：** 拖拽引擎（lib/dragOperation）`begin()` 未做 pointer capture——item 上按下后鼠标划出窗口松手，`pointerup` 不派发到 webview，sess 变僵尸（`onWindowBlur` 兜底只在窗口**失焦**时触发，划出划回不失焦就漏）。僵尸 sess 被后续按下经 `if (sess) return` **静默复用**：移动超 6px 阈值误 `startDrag`——① `suppressClick` 吞掉紧随的 click（点击无效；原地双击位移小不触发，故"双击才行"）；② `startDrag` 内 `clickFolder` 把无关文件夹误入选择域，之后点当前快速访问项走 `openView` 等值 return 分支不清域（双选中残留）；③ 严重时执行意外 drop（静默移动文件）。
- **解法：** 三道防线互补——① **治本**：begin 时对按下的 `.tree-item/.asset-card/.list-row/.folder-card` 根元素 `setPointerCapture`（窗外松手 pointerup 也能收到；capture 到自身根元素不影响 click 派发——down/up 共同祖先仍是他；**切勿 capture 到 documentElement**——共同祖先变根会让 click 派发到根，纯点击全灭），endDrag 释放；② `onMove` 首行 `(e.buttons & 1) === 0` 立即 `endDrag(true)`——pointerup 丢失的僵尸在下一个 move 即刻自清；③ begin 里 sess 已存在先 `endDrag(true)` 再建新（不静默复用）。另修次要路径：FolderTree 的 `nextTick(clickFolder)` 加 `sidebarSelected === folder:id` 守卫（连点"树 item → 快速访问"同 tick 切走时不再误入域残留描边）。
- **预防：** 手写 pointer 拖拽引擎三件套必须齐：capture（或等价窗外 up 保证）/ buttons 活性检查 / 会话重建护栏；window 级 up 监听永远会丢（窗外松手、系统抢指针），不能只靠 blur 兜底。

## 034 std::process::Command 自动引号转义 vs explorer 原始命令行解析（/select 回退"文档"）

- **现象：** 2026-08-14 序列帧"在资源管理器打开"（文件名含空格）恒跳"文档"文件夹——explorer 对解析失败的路径静默回退，无报错。
- **原因：** 两层叠加。① 裸路径含空格时 explorer 自解析截断；② 手写 `format!('/select,"{path}"')` 经 `std::process::Command::arg` 传递时，**Rust 自动给含空格参数加外层引号、内层引号转义为 `\"`**——而 explorer.exe 不走 CommandLineToArgvW（吃原始命令行），转义后的 `\"` 直接断路径。PowerShell 直传同字符串能成功（原样传递），对比实验才定位到这一层。

- **预防：** Windows 下调系统程序传**预格式化参数字符串**（含引号的开关参数）时，不要用 `Command::arg`（它按 argv 语义再加工）；用 ShellExecuteW 或 `CommandExt::raw_arg`（原样拼接）。诊断注意：git bash 传中文参数有编码失真，验证此类问题用 PowerShell 起进程才可信。

## 035 pointer capture 挂太早：begin 即 capture 会把 dblclick 重定向，名称区双击改名被吞成"打开"

- **现象：** 2026-08-18 用户实机：双击素材卡 / 文件夹卡的**名称区域**不进出改名，反而触发卡片级双击行为（素材开预览 / 文件夹进入）。
- **原因：** 032 的僵尸会话修复把 `setPointerCapture` 挂在拖拽引擎 `begin()`（每次左键按下即挂到卡片根元素）。capture 生效期间**全部指针事件（含兼容鼠标事件 click / dblclick）重定向到 capture 元素**——双击序列第二击与 dblclick 落到卡片根：名称 span 的 `@dblclick.stop` 永远收不到，卡片根的 dblclick（预览 / 进入）照触发。032 注释"capture 到根元素不影响 click 派发"对 click 成立（选中本就绑在卡片根），对 dblclick 子元素分发不成立。

- **预防：** pointer capture 的挂载时机 = 手势确认的那一刻，不是按下那一刻；按下即 capture 会吞掉一切"按下发源于子元素"的高层事件（dblclick、contextmenu 同理）。验证拖拽引擎改动必跑 cdp-drag-zombie-probe（S5 真拖拽）+ 双击改名探针用例（cdp-card-interact-probe S4/S6）。

## 042 ffmpeg-next scaler.run 输出帧 buffer 尺寸不符即报错丢帧：热改输出尺寸必须连输出帧一起重建

- **现象：** 2026-08-20 帧流出帧尺寸热更新（卡片跟随显示尺寸）首版：运行期改目标尺寸后后续帧全部消失（`no_upscale_and_live_resize` 用例只收到改尺寸前的帧）。

## 043 ShellExecuteW "openas" 动词未注册返回 31（SE_ERR_NOASSOC）：「打开方式」对话框要备 rundll32 兜底

- **现象：** 2026-08-20 用户实机：素材右键「在其他应用打开」报"打开方式对话框调用失败，错误码 31"。

- **现象：** 2026-08-21 用户实机报"回收站的单选选中、双击名称改名等基础操作被改坏了"。探针首跑（`dispatchEvent(new MouseEvent('click'))`）却全绿——合成 click 不经 pointerdown 链，量不出这条缺陷。

- **解法：** 回收站视口卡片按下**直接 return 放行**（不起拖拽、不交框选）——click 正常合成选中；框选不受影响（空白处按下照常发起）。
- **预防：** ① **点击类探针一律用 `Input.dispatchMouseEvent` 真实事件**（pointerdown→pointerup→click 全链），`dispatchEvent(click)` 只在验证纯状态逻辑时用——凡涉 pointer 链路的交互（选择 / 拖拽 / 框选 / 重命名）合成事件会绕过真链路给出假 PASS；② 手势分发层（gridPointerDown）分流到"带 preventDefault 的回调"前必须想清楚 click 还要不要活。


## 047 ffmpeg-next `frame.plane::<f32>()` 长度 = samples() 不含声道数：立体声交错只取一半（5.3 音频解码实测）

- **现象：** 2026-08-22 5.3 视频 PCM 音频链联调：重采样输出立体声 1098 样本/声道，按 `plane::<f32>(0)[..n*2]` 取交错数据直接越界 panic（range end index 2196 out of range for slice of length 1098）。
- **原因：** ffmpeg-next 的 `frame::Audio::plane<T>()` 切片长度恒 = `samples()`（每声道样本数），**不乘声道数**——packed 立体声的实际数据是 n×2 个 f32 交错，plane 只返回前一半。语义陷阱：名字像"整平面"，实现是"按样本计"。
- **解法：** 绕开 plane()：`frame.data(0)`（linesize 字节切片）→ `from_raw_parts(ptr as *const f32, n * 2)` 手工切（decoder.rs `f32_plane` 助手钉注释）；planar 格式另行按声道取 data(i)。
- **预防：** ffmpeg-next 音频帧读数据一律走 data()/字节层，plane()/plane_mut() 只在"每声道独立平面且逐声道处理"时按样本数理解；写 AV 解码新代码时先跑带立体声的单测（本坑由 audio_resample_chunks / decode_video_with_audio 两测试当场暴露）。

## 048 ffmpeg-next `frame.timestamp()`（best_effort_timestamp）不回落 pts：手造帧判空要点

- **现象：** 2026-08-22 重采样单测手造 Audio 帧 `set_pts(Some(...))` 后 `timestamp()` 恒 None，push_audio 早退、0 块产出（测试全灭但无报错）。
- **原因：** 新版 FFmpeg 的 `best_effort_timestamp` 是 AVFrame 独立字段（解码器写），`av_frame_get_best_effort_timestamp` 只读它、**不再回落 pts**；手造帧 set_pts 写的是 pts 字段，两字段互不通。
- **解法：** 读时刻统一 `frame.timestamp().or_else(|| frame.pts())`（生产解码器恒有 best_effort，回落只为测试与怪容器兜底）。
- **预防：** 凡是"读帧时刻"的代码都按双字段兜底写；测试手造帧用 set_pts 即可覆盖同一条路径。


## 049 性能/体感结论必须真机数据先行——仿真探针全绿而实机卡死（5.3 裸帧流一日弯路的总根因）

- **现象：** 2026-08-22 5.3 视频帧流三轮落地，桩探针 + 真后端探针全 PASS（66 帧/3s 无 >100ms 间隙、seek 端到端 737ms）；用户实机却是 scrub 等 1-2s、预览播放冻结、音画错位 1-2s、画面模糊——"探针越绿，实机越卡"。
- **原因：** ① 探针从未连真实渲染环境（headless Edge + 桩命令 + 假 WS 帧源），量的是"通道能跑"不是"用户体验"——真实 WebView2 的主线程合成、DPR、GPU 通路全部缺席；② 测试样本（4K120 录屏）与用户真实文件（1080p25 长 GOP 成片 199MB）负载形态不同；③ 更上游的误诊链：5.1 复核时把"scrub 卡"归因为"`<video>` 不行、需要自研解码器"，**当时没有量过 `<video>` 通道本体的任何数据**——方向终版前的真机 spike（spike/video-seek/probe.py）实测 asset protocol Range 完好：1080p25 seek 5-40ms、66ms 连发 scrub 25/25 全跟手，通道根本没病，病在交互层（踩坑 050）。

- **预防：** ① 性能/体感类结论一律"真机数据 → 方案"，探针 PASS 只证逻辑正确不证体验达标；② "X 不行要换 Y"的架构判断前必须先量 X 的本体数据——不量就换等于猜；③ 实机复现用的样本要覆盖用户真实文件形态（时长 / GOP / 码率 / 分辨率），别拿合成样本当结论；④ 反向同样成立——**长跑 dev server 上的探针 FAIL ≠ 代码回归**（2026-08-22 晚实证：用户复验用的 dev server 长跑 2h + 多轮 HMR 后，cdp-anim-stream-probe 尺寸跟随断言两次假 FAIL / 一次卡死；干净 vite 实例同代码秒过）——探针复跑先换干净 dev server 实例再怀疑代码；⑤ 同族再补——**探针吊死 ≠ APP 回归**（2026-08-23 实证：干净实例上 cdp-anim-stream-probe 两轮吊死在滚轮注入段，根因 = 探针 frame_server 单线程事件循环推流与 CDP recv 互饿的已知结构瓶颈（探针注释在册），100ms 进入延迟档滚动中 WS 连接变密 + 本机 dev 全套在跑放大触发，降帧率/滚速未救回）。处置顺序：吊死先看输出停在哪个场景、该场景覆盖的代码本轮是否触碰——未触碰则以"已过场景 + typecheck + 实机复验"收尾，不为仿真环境硬磕。


## 050 timeupdate 仅 ~250ms 粒度且拖动中回写覆盖目标值——scrub"连 UI 都卡"的体感与解码无关

- **现象：** 2026-08-22 晚回滚 `<video>` 后用户复验："scrub 不跟手、跳动感明显、切换慢，连 UI 都卡住了"；实测 seek 本体 5-40ms 无病。
- **原因：** ① 悬停 scrub 的底部进度条 / 帧号胶囊只走 `timeupdate` 事件更新——Chromium 每 ~250ms 才发一次，UI 以 4fps 跳变，肉眼即"卡"；② 播放条拖动中 `seek()` 乐观写入目标值后，`timeupdate` 持续用元素实际位置回写 store——快速拖动时进度条被往回拽（弹回）。
- **解法：** Eagle 式"进度条剥离"（用户点破：Eagle 进度条是剥离出来的，滑动流畅因 UI 不等解码）——拖动/scrub 期间 UI 以鼠标位置为准立即渲染：`previewMedia.scrubbing` 标志（pointerdown/up 置位，pointercancel 兜底）拖动中 timeupdate 不回写、松手对齐真实位置；HoverVideoLayer.onScrub 设 `v.currentTime` 后同步写本地 currentTime。
- **预防：** ① 媒体元素状态与拖动中 UI 状态分层：拖动中 UI 跟手势、元素异步追、timeupdate 类低频事件只在非拖动期同步；② 记牢 timeupdate 是 ~250ms 粒度不是逐帧——任何"跟手"诉求都不能经它转发；③ 修"卡"先分清是数据慢还是 UI 慢，两者药方完全不同。


## 051 WebView2 远程调试：WEBVIEW2_ADDITIONAL_BROWSER_ARGUMENTS 被 wry 显式参数覆盖，CDP 端口须走 tauri.conf additionalBrowserArgs

- **现象：** 2026-08-22 真机 spike 前置：tauri dev / 直跑 app.exe 带 `WEBVIEW2_ADDITIONAL_BROWSER_ARGUMENTS=--remote-debugging-port=9223`（bash 前缀 / cmd set 两法皆试），9223 恒不 LISTEN，msedgewebview2 browser 进程命令行无该 flag。

## 052 image crate 0.25 按扩展名预设解码格式（假扩展名文件 InvalidSignature）

- **现象：** 2026-08-23（5.4 实机走查）用户报"有的 PNG 格式不支持"——样本为壁纸站下载的 .png 文件，魔数实为 JPEG（FFD8FF），自定义缩略图报"该文件无法用作缩略图"。
- **原因：** image 0.25 的 `image::open` / `image::image_dimensions` 内部 `ImageReader::open` **按路径扩展名预设 format**，随后的 `with_guessed_format` 只在 format 为 None 时才按内容魔数猜测——扩展名撒谎时魔数猜测被跳过，PNG 解码器读 JPEG 流报 InvalidSignature。
- **解法：** 绕过 open 的扩展名预设，手动构造无预设 reader：`ImageReader::new(BufReader::new(File::open(p)?)).with_guessed_format()`（format = None → 恒按内容魔数）。thumbnail 的 probe / load_origin 已改此口径（probe_by_signature / decode_by_signature，导入与缩略图三件套同愈），回归用例 `fake_extension_decodes_by_content_signature`。
- **预防：** 用户渠道文件扩展名不可信（壁纸站 / 改后缀收藏常见）；凡"按文件内容判定格式"的场景走魔数版 helper，别再直接用 `image::open` / `image::image_dimensions`。

## 053 CDP 探针桩返回可变 DB 集合必须深拷贝——共享引用绕过 Vue 响应式（双 item / 编辑不刷新假象）

2026-08-23，6.2 关系探针攻关六轮。症状链：add 成功后详情面板渲染**两条相同 item**（store 数组确有 2 条同 id 记录）+ 二次修改提交后 store 数据已新、DOM 恒旧。

根因 = 桩 `list_relations: () => DB.relations` **原样返回桩数组引用**：前端 store 数组与桩 DB 是同一对象——① 桩侧 add 的 `DB.relations.push` 直接写进前端 state（绕过 Vue 代理不 trigger），前端 confirm 再 push 一次 → 双 item；② 前端 `this.relations = DB.relations` 刷新赋值是同引用 → Vue `Object.is` 判定不 trigger → 编辑不刷新。**产品环境（真 IPC 序列化返回全新对象）两者都不成立**，纯探针 artifact。

修法：桩返回 `JSON.parse(JSON.stringify(...))` 斩断共享。**教训**：桩造可变集合（list 系命令）一律深拷贝；get 系返回字面量对象无此问题（每次新建）。**2026-08-24 同型再犯（6.2 链接管理探针）**：桩 `list_placements: () => DB.placements` 未深拷贝——sync_asset_links 桩真改 DB 后前端 refresh 拿到同引用数组不 trigger，视图恒旧数据；关系探针当时只深拷贝了 list_relations，**桩会写数据的集合都要深拷贝，不只 relations**（速查表 §12 桩纪律已补强）。同场再验既有坑：多文件改动探针前**批量 touch**（vite watcher 漏变更，探针拿旧模块白跑五轮）；v-for 内模板 ref = 数组收集（`ref.value[0]`，直调 `.select` 抛 TypeError）。

## 054 后台 `pnpm dev` 收工后 vite 子进程成孤儿占端口（TaskStop 只杀 pnpm 壳）

- **现象：** 2026-08-28（阶段七预览页截图）。后台任务 `pnpm dev` 用 TaskStop 收工显示 killed、netstat 查端口也已释放，过几分钟再起 `pnpm dev` 却撞 `EADDRINUSE`——vite 子进程（独立 node PID）在 TaskStop 后才脱离壳进程继续监听，首次查端口时它还没完全起来/暂未 LISTEN，漏检。

## 055 grid `0fr→1fr` 宽度推挤动画只适用外部定宽容器——自适应容器里 0fr 轨道仍占 max-content 宽度

- **现象：** 2026-08-29（阶段七十轮，拉下按钮-横向）。容器内容自适应（inline-flex 无显式宽）时，未展开项包 `display: grid; grid-template-columns: 0fr` + 内层 overflow hidden——视觉内容确实被裁掉了，但**容器宽度仍按全部项的 max-content 撑开**：收起态容器带着隐藏项的宽度，选中项与箭头之间一大段空白，"间距全乱"。同机制在 item 族卡片（`.ni-slide`，卡片定宽 240）里完全正常，迁到自适应容器就露馅。
- **根因：** 0fr 在"外部给容器定宽、轨道按比例分配"时才把轨道压到 0；容器走内容自适应（max-content 贡献计算）时，fr 轨道的贡献 = 内容的 max-content——0fr 不减少它。宽度本身就是内容决定的，没有"外部约束"可压。
- **解法：** 自适应容器做宽度展开动画 = **JS 实测内容宽 + 显式 `width` 过渡**：内层 `width: max-content`（任何状态下 offsetWidth 都可测真实内容宽），onMounted 收集各项宽度进响应式数组，wrap 按显隐内联 `width: Npx / 0px` + transition；测量完成前禁 transition（`ready` 类挂载后 rAF 开启）防首帧闪动画。间距用内层左 padding（随宽度一并被裁），不用 flex gap（对 0 宽项不折叠留缝）。
- **预防：** 凡"宽度动画展开/收起"需求，先判容器宽度语境——外部定宽/剩余空间分配 → grid 0fr→1fr 最简；内容自适应 → 实测宽度方案。预览页 demo cell 默认 `align-items: stretch` 还会把自适应宽组件拉宽到 caption 宽，掩盖/放大此类问题（本轮 preview.css 已改 flex-start）。

## 056 CDP 探针连上历史僵尸 headless Edge——固定调试端口 + terminate 只杀父进程（旧页面旧模块鬼状态）

- **现象：** 2026-08-29（阶段七十五轮，悬浮栏走查修复验证）。探针连跑四轮全 FAIL 且证据互相矛盾：静态宽度新旧值混杂（force-focus 实例一会儿 450 一会儿 250）、console 异常时间戳逐轮**完全雷同**、组件 setup 报 `watch is not defined`（磁盘文件明明已导入）。同代码用一次性 debug 脚本（随机端口）全正常。

## 057 云母 Mica 接入：`show()` 前 `set_effects` 吞掉 WebView2 全部内容（只剩云母渐变）

- **现象：** 2026-08-30（阶段七 7.1 十七轮，主窗口骨架轮）。transparent 窗口 + `set_effects(Mica)` 在 `show()` 之前调用：窗口只剩云母渐变、**UI 完全不可见**（DOM 完整渲染、computed 样式全对，屏幕上看不到）；同一窗口运行中热切换 Mica 则 UI 与云母共存正常。伴随矩阵实测（Win11 25H2 build 26200 + WebView2 152）：`transparent:true + shadow:true` 冷启动吞 UI；`transparent:true + shadow:false` UI 恢复但**纯透明穿透**（透出下方窗口清晰文字，Mica 无处可画）；`transparent:false + backgroundColor #00000000` 时 WebView2 透明露窗口 GDI 黑底（重定向表面无 alpha 通道，Mica 画不出）。
- **根因：** Tauri 在 Windows 的 `transparent` = 仅设 WebView2 `DefaultBackgroundColor` 透明（wry 层），窗口本身无 LAYERED/NOREDIRECTIONBITMAP；Mica（`DWMWA_SYSTEMBACKDROP_TYPE`）由 DWM 在窗口显示路径就绪后才能正确与 DCOMP 内容合成——初始化早期设置时序错位，内容表面被吞。
- **解法：** **`set_effects` 一律在 `show()` 之后调**（lib.rs `apply_main` 置于 show/set_focus 之后）；诊断期实证 SYSTEMBACKDROP_TYPE=2 + UI 完整 + 93% 底透出 7% 云母。窗口配置终态 = `transparent:true + shadow:true`（shadow 的 NCCALCSIZE insets 机制与 Mica 无冲突）。
- **2026-08-30 063 六轮修订：** 上述"终态"被推翻——`transparent:true` 的 blur-behind 空 region hack 让含非客户区的整窗表面按 alpha 合成，DWM 圆角描边曲线与方形客户区角之间的月牙窄缝 alpha=0 成透底洞（详见 063）。新终态 = **`transparent:false + backgroundColor:#00000000 + shadow:true + DwmExtendFrameIntoClientArea(-1)`**（Mica 由 DWM 在窗口表面底下合成，不需要 tao transparent；真正需要透明的只有 WebView2 默认背景）。本条"transparent:false 露 GDI 黑底、Mica 画不出"的旧结论是在无 ExtendFrame + show 前 set_effects 的矩阵下测得，六轮实机验证新组合 Mica 正常、月牙缝消失。

## 058 flex/grid 容器的 trailing gap 被 Chromium 计入 scrollHeight——高度展开动画终值偏大，切回 auto 瞬间兄弟回弹

- **现象：** 2026-08-30（阶段七十八轮，树容器展开动画）。最外层父级展开时，被推下去的兄弟层级在动画收尾"回弹一下"。cdp-tree-expand-probe 逐帧采样实证：`.ft-children`（flex column + gap 2，3 子项 26 高）`getBoundingClientRect().height` = 82，而 `scrollHeight` = **84**——多出一个 trailing gap。展开动画 0→84px 补间，transitionend 后清 inline height 切回 auto（82），兄弟从 +86 跳回 +84 = 2px 回弹。

- **预防：** 凡"实测元素高度驱动 JS 补间"的代码，先想测量值是否等价于 auto 布局高——scrollHeight 在 flex/grid gap 容器上恒偏大；写动画探针断言兄弟位移时把"超调量 ≤1px"列进去（本坑靠 overshoot 断言直接显形）。

## 065 伪元素当背景层必须沉底：absolute 无 z-index = 层叠第 6 层盖正常流内容（2026-08-31）

- **现象：** 7.1 二十三轮走查——右栏 g1 底色改 `::before` 只画顶行以下后，用户实机报封面编辑「更换封面 / 取消 / 确认」与底部「信息查看管理」钮**看不到但能盲点**（点「更换封面」位置菜单能弹出）。
- **根因：** `::before { position: absolute }` 无 z-index → CSS 层叠第 6 层（z-index auto 定位元素档），绘制在正常流内容（第 3/5 层）之上 → 右栏所有无定位元素被 g1 伪元素盖住；`pointer-events: none` 让 hit 测试穿透 → 「能点不能看」。带 position 的元素（relative 的封面框 / 输入框 / 分段控制器 / tab 滚动区）同第 6 层且 DOM 序在后，侥幸可见——现象呈「部分元素消失」，极具迷惑性。
- **修法：** aside 加 `isolation: isolate`（自建层叠上下文，不依赖外层上下文状态）+ `::before` 加 `z-index: -1`（沉到正常流之下）。
- **预防：** ① 伪元素当背景层 = `isolation: isolate` + `z-index: -1` 配套写，别只写 absolute；② **computed 样式与几何断言测不出层叠遮挡**——元素在、尺寸对、就是被盖；改背景层/层叠结构后必须截图目验关键交互件（按钮！），探针 R13c 封面编辑态截图 + R4c2 沉底断言钉死。

## 066 存在性判断误用 `iter().all(==)`——空表/全匹配两极端都成立，懒建变重复建档（2026-09-01）

- **现象：** 7.1 二十三轮走查续——用户实机报「角标改名后，中间面板卡片的角标消失了」：右栏详情面板显示新角标正常，网格卡片角标整个不见。
- **根因：** `set_archive_cover_settings` 记录懒建条件误写 `archives.iter().all(|a| a.folder_id == folder_id)`——`all` 在**空迭代器上恒 true**、在**全表皆本档案记录时**也 true：用户库里恰只有这一个档案有记录，每次确认封面都追加一条同 folderId 空壳副本。读侧不对称把 BUG 伪装成「改名丢失」：详情 `get_archive_data` 用 `find`（首条 = 真数据，面板显示新值正常），卡片 `list_archives` 全量返回、前端 `map[folderId] = a` **后写覆盖** → 空壳副本赢，角标/属性全空。同条件在「他档有记录、本档无」时 all 不成立 → 懒建跳过 → 紧随的 `.expect()` 直接 panic（未爆只是没走到）。
- **修法：** 条件改 `all(|a| a.folder_id != folder_id)`（custom_data.rs 既有正确口径——「全都不是」=「不存在」）；存量坏数据由开库自检 `fix_archives` 加**同 folderId 去重保留首条**自愈（更新永远落 find 命中的首条，后追加的副本必为陈旧空壳）。
- **预防：** ① 写「不存在则 X」判断就用 `!iter().any(==)` 或 `iter().all(!=)`，**禁用 `all(==)`**——空表语义反直觉（vacuous truth）；② 同一数据有 find-first / 全量-list 两条读路径时，写侧 BUG 会呈「一处正常一处丢」的假象——排查先比对两条读路径各自拿到哪条记录；③ 回归测试要覆盖「列表非空但无本档」与「唯一记录即本档」两个极端（原测试只测空表懒建，全匹配分支漏网）。

## 067 前后端「同一约定」必须含长宽比——取景框方形化后烘培仍出 13:10 = 确认后二次裁剪（2026-09-01）

- **现象：** 用户实机报封面设置「选好了取景框，确认后又裁剪了一次」：编辑态预览显示的区域与确认后成图不一致（成图约放大 1.3×）。
- **根因：** 7.1 新稿封面框改方形 240×240，前端取景数学按方形框算（`z0 = max(F/w, F/h)` cover 铺满）；后端 `bake_cover` 输出仍沿旧 43 稿 416×320（13:10）——`COVER_OUT_W/H` 参与窗口数学（`z = max(W/iw, H/ih)·scale`），**长宽比不同 = 可见窗口不同**：方形源图 scale=1 时前端窗口 = 全图，后端窗口竖向只有 76.9%；烘出的 13:10 图再被方形展示框 `object-fit: cover` 左右裁一刀，两刀叠加 = 「又裁了一次」。注释里写「crop 语义与像素无关」对**比例**不成立——x/y/scale 都是相对框的分数，框比变了语义就变。
- **修法：** 烘培输出改 416×416 方形（与框同比例，前后端公式恒等；存量 13:10 封面重设即更新，不做迁移）。
- **预防：** 跨端共享的几何约定（取景/裁切/坐标归一），契约三要素写全：**基准框尺寸或比例 + 偏移语义 + 缩放基准**——改任何一端的框比例，先 grep 另一端吃这个参数的所有常量；UI 改版改了几何载体（如 13:10 → 方形），必须回查所有以它为基准的下游计算。

## 068 ffmpeg libwebp 动画编码差分帧产物本身带残影——解码端缺陷定性只是冰山一角（2026-09-02）

- **现象：** 小动画缓存（ffmpeg sidecar 转码 animated webp）在卡片 `<img>` 播放时"所有帧都重叠"——CEP 伴生 webp（大透明区角色动画）必发，GIF（不透明全帧）无恙；同源 origin 走帧流/帧条（image-webp 解码）却正常。
- **定性链：** ① Pillow（libwebp 参考实现）规范合成转码产物第 4 帧起即带残影 → **产物帧本身就错**（排除 Chromium 播放缺陷、排除 image-webp 解码缺陷）；② ffmpeg 解码 origin 输出 PNG 干净 → 解码环节无恙；③ 坐实 **ffmpeg libwebp 编码差分帧（矩形裁剪 + blend/dispose 组合）生成错误**。2026-09-01 曾把同类重影定性为"image-webp 画布合成缺陷"——那只是差分帧危害链的一环：**不合规的差分产物在任何解码端都可能叠影**。
- **修法：** 小动画转码链整体弃用 ffmpeg sidecar，改纯 Rust 编解自洽——`anim::decode_frames`（完整画布帧）→ `shrink_to_edge` 缩放 → `anim::encode_webp_anim` 全帧组包（blend=0 全画布矩形，与 CEP 导出同一口径）；存量坏缓存由 `is_fresh` 加**全帧组包结构判定**（逐 ANMF chunk 校验 x=0,y=0、矩形=全画布、flags bit1=1——无版本戳可判时的结构特征口径）自动翻新重生成。
- **预防：** ① 转码类产物**必须经第二个独立解码端验证**（本例 Pillow 一测即现形，ffmpeg 自解自产物测不出来——编解同体的缺陷互相掩盖）；② 带 alpha 的动画编码是高危区：差分优化（矩形裁剪/blend/dispose）+ 有损 alpha 的组合，编码器实现质量参差，输出全帧组包（blend=0 源覆盖）是消除变量的终版姿势；③ 缓存类文件要翻新存量时，结构特征判定（文件内部格式指纹）比版本戳/mtime 更可靠。

# 06_踩坑记录

> 四段式：现象 / 原因 / 解法 / 预防。踩到即记，写完把能沉淀的预防措施补进 `01_开发规范`。

## 021 Vue SFC scoped 块内 `:global(x)` 带后代选择器被吞：拖拽时整窗黑屏

- **现象：** 拖拽卡片一开始整个窗口全黑（只剩窗口边框），松手立即恢复——像渲染崩溃，实为 CSS 事故。
- **原因：** AssetCard scoped 样式块内写 `:global(body.dragging) .thumb .actions { opacity: 0 }`，**SFC scoped 编译把 `:global()` 后面的后代选择器吞掉**，产物只剩 `body.dragging{opacity:0;pointer-events:none}`（dist CSS 实证）。拖拽开始 body 加 dragging 类 → 整个 body 透明度归零、只剩窗口底色 = 全黑，松手移除类即恢复。
- **解法：** 全局规则改写到独立的非 scoped `<style>` 块（`body.dragging .asset-card .thumb .actions`）——类名在 scoped 编译产物中原样保留可正常匹配；特异性算足（(0,4,1) 压过 `.asset-card:hover .actions` (0,4,0)），构建后 grep dist CSS 验证产物。
- **预防：** scoped 块内 `:global(...)` 必须整包完整选择器、不能带后代；要影响全局（body 类切换等）一律写非 scoped 块或全局样式表；写这类"看不见"的规则（opacity / visibility / display）后 grep 一次 dist CSS 确认编译产物没变形。

## 020 vite 起不来：listen EACCES——端口被 Windows NAT 动态保留段覆盖

- **现象：** `pnpm tauri dev` 失败：`beforeDevCommand terminated with non-zero status`；手动 `pnpm dev` 报 `Error: listen EACCES: permission denied 127.0.0.1:5173`——不是 EADDRINUSE（无进程占用 5173），昨天还能正常 dev。
- **原因：** Windows NAT（Hyper-V / WSL / Docker 的 winnat 服务）会动态保留 TCP 端口段，`netsh interface ipv4 show excludedportrange protocol=tcp` 可见 5173 落在 5144-5243 保留段内；保留段随系统重启 / winnat 重启漂移，所以"昨天好的今天不行"。
- **解法：** 换保留段外端口：vite.config.ts `server.port` 5173 → **5373** + tauri.conf.json `devUrl` 同步（两文件必须一起改，否则 Tauri 一直 Waiting for frontend dev server，同踩坑 002 的联动）。
- **预防：** dev 报 EACCES（非 EADDRINUSE）先查 excludedportrange 再查占用；端口变更必须 vite.config.ts 与 tauri.conf.json 同步；若保留段漂移再次覆盖 5373，同法再换（也可用 `net stop winnat` 重置保留段，需管理员且重启后可能复发，不作首选）。

## 019 增量链接缓存损坏：LNK2019 "无法解析的外部符号 anon…" 挡住 dev 启动

- **现象：** `cargo test` / `pnpm tauri dev` 编译末期链接失败：`error LNK2019: 无法解析的外部符号 anon.{hash}.llvm.{hash}`（serde Serialize/Deserialize 等泛型符号），报 N 个无法解析后 `fatal error LNK1120`、`could not compile 'app' (lib)`；代码本身无任何问题，且错误符号与本次改动无关。
- **原因：** Rust 增量编译的代码生成单元缓存（`target/debug/incremental/`）与前一次编译状态不一致（本机 2026-07-28 一天内出现 2 次；opt-level=1 的 dev profile + cdylib 组合下偶发）。
- **解法：** `rm -rf src-tauri/target/debug/incremental` 后重跑即可（只清增量缓存，依赖与 crate 产物保留，重编约 1 分钟）；不要 `cargo clean`（全量重编 10 分钟级）。
- **预防：** 遇到"符号与改动无关"的 LNK2019 先清 incremental 再怀疑代码；若日后频繁复发，再考虑 `[profile.dev] incremental = false`（代价是每次改代码重编 app crate 从秒级变分钟级，暂不关）。

## 018 LGPL ffmpeg 构建没有 libx264：转码静默失败

- **现象：** 导入 mov 后预览报"该格式暂时无法播放"，转码兜底没生效；手动跑 sidecar 才发现 `libx264` 编码器不存在。
- **原因：** 5.1 选型特意用 BtbN **LGPL** 静态构建（避免 GPL 传染），而 x264 正是 GPL 许可——LGPL 构建不含 libx264。写转码参数时按惯性填了 `-c:v libx264`，ffmpeg 因编码器缺失非零退出。
- **解法：** 改用 LGPL 构建内可用的 h264 软编码器 `libopenh264`（Cisco，BSD 许可，无传染）——注意它不支持 x264 的 crf/preset，用 `-b:v` 码率控制；`-encoders` 列表核对过 libvpx-vp9 / 硬件编码器（h264_mf / nvenc / qsv）也在但前者太慢后者依赖机器，不作首选。
- **预防：** 给 sidecar 写编解码参数前，先用 `-encoders` / `-decoders` 核实该构建实际带了什么；许可选型（LGPL）与功能清单是一体的，改构建变体时必须重核。

## 017 dev 构建性能误判：慢的是 O0 不是管线

- **现象：** dev 模式（`pnpm tauri dev`，cargo debug 构建）下动图帧条 18 帧要 5-10 秒、CPU 风扇猛转；序列帧 17 张"秒读"。排查方向一度以为是架构问题（帧条反复解析 GIF / 等解包 / 大图二次解码）。
- **原因：** 纯 debug（opt-level 0）的图像解码 / 重采样比 release 慢 10-30 倍，基准实测 1080p webp 帧条 O0 = 725ms/帧 vs release = 43ms。两层叠加：① 依赖 crate 内的解码（webp 解码 455ms）；② **泛型函数在调用方单态化**——imageops::resize 的代码生成在我们 crate（O0）而非 image crate，只给依赖开优化管不到它（261ms）。序列帧"秒读"只是因为 PNG 小图基数小。
- **解法：** Cargo.toml `[profile.dev] opt-level = 1`（管泛型单态化）+ `[profile.dev.package."*"] opt-level = 2`（管依赖内部代码），效果 725→57ms/帧，与 release 同量级；依赖只编一次，日常增量构建不受影响。
- **预防：** dev 模式下任何"慢"的结论先隔离构建配置变量——性能判定以 release（或 O2 基准）为准，优化需求先在 release 复测再立项；dev 优化配置已固化 Cargo.toml（图像基准 thumbnail.rs bench_frame_strip_stages #[ignore] 可复跑）。

## 016 GIF 元数据探测用解码级遍历：导入大 GIF 卡数秒

- **现象：** 导入一个几十 MB 的 GIF 要等好几秒才出卡片，小图却无感。
- **原因：** `anim::probe_gif` 用 image crate `into_frames()` 逐帧**解码像素**来数帧数、累加时长——GIF 格式没有全局帧数头，要数帧必须遍历整个文件，而 image crate 只提供解码级遍历，探测成本 = 完整解码一遍。
- **解法：** 改纯字节级扫描（scan_gif）：按 GIF 块结构跳块——0x2C 图像描述块数帧、0xF9 图形控制扩展拿 delay 累加时长、色表与 LZW 子块链按长度跳过，只读字节不解码；与 image crate 解码结果做交叉校验单测防解析偏差。探测从"解码一遍"降为"读一遍"，导入零等待。
- **预防：** 格式探测（probe）只允许"读一遍文件"量级的开销，禁止解码级操作；帧数/时长确实要遍历才能拿到的格式，用字节级块扫描，把解码留给真正需要像素的环节（缩略图 / 解包）。

## 015 视觉类目检用合成样本：口径缺陷被掩盖

- **现象：** 音频波形渲染迭代十几轮，用 ffmpeg 合成的 8 秒噪声样本目检一直"通过"，用户真实 3 秒配音文件却整体发淡、峰值无辨识度。
- **原因：** 渐变叠加机制的效果强依赖"文件时长 / 窗口数"比例——长文件每窗口样本多、纵线长且重叠，合成样本看着正常；用户短文件每窗口仅 ~2 样本，纵线短且散，叠不出实心主体。合成样本的统计特性与真实素材完全不同。
- **解法：** 取用户参考版音频本体跑候选算法**逐像素比对**（`tools/waveform-match.py`），匹配度 95%+ 才定稿；不再凭合成样本目检下结论。
- **预防：** 视觉 / 渲染类功能验收，样本必须用用户真实文件（覆盖最短 / 最长 / 最静 / 最响两端），合成样本只能做逻辑单测，不能做观感目检（呼应 012 "新格式接入先用用户真实样本验证"）。

## 014 测试 exe 链接 tauri GUI 依赖链：0xc0000139 入口点未找到

- **现象：** preview_queue 测试持有 `AppHandle` 后，Windows 上测试 exe 加载即失败（STATUS_ENTRYPOINT_NOT_FOUND），全部测试无法启动。
- **原因：** 测试代码经 `AppHandle::emit` / 析构把 tauri GUI 依赖链（rfd 的 `comctl32!TaskDialogIndirect` 等）拉进测试 exe，而测试 exe 无 comctl32 v6 清单（tauri-build 只给主程序内嵌），System32 的 v5.82 无此导出。build.rs `/MANIFESTINPUT` 与 tauri-build 清单资源冲突、`#[link(+whole-archive)]` LNK1356，均不可行。
- **解法：** AppHandle 字段与 emit 实现 `#[cfg(not(test))]`，测试构建起无事件实例（`start(None)`，句柄 mem::forget 丢弃）——生产路径行为不变。
- **预防：** services 层需要 AppHandle（事件 / 窗口）时，一律走"Option 句柄 + cfg(test) 空实现"模式，测试不碰 tauri GUI 类型；命令层测试调私有逻辑函数，不直接构造 AppHandle。

## 013 Tauri v2 非 async 命令在主线程执行——主线程内 build 窗口死锁

- **现象：** 预览"新窗口打开"点击后整个进程卡死——主窗口无法拖动/关闭、托盘菜单无响应；新窗口出现但不渲染内容、压在主窗口下方。
- **原因：** Tauri v2 中**未声明 async 的命令在主线程执行**。`open_preview_window` 是 sync 命令，在主线程内 `WebviewWindowBuilder::build()`，窗口创建流程与主线程事件循环互等，主线程死锁。
- **解法：** 命令改 `pub async fn`（线程池执行，build 内部 dispatch 回主线程不阻塞——官方 multiwindow 示例路径）；preview 模块 5 条命令一并 async 化（list_sequence_frames 帧条小图生成等 IO 重活也不该占主线程）。
- **预防：** Tauri v2 命令默认主线程执行——**凡涉及窗口创建 / IO 重活 / COM 调用的命令一律 async**；纯内存快操作（取锁读索引）才用 sync。新增命令时对照本条自查。

## 012 PSB 结构判定看签名（8BPB）而非版本号

- **现象：** 公司工具链导出的 PSB 素材（879×1016）导入后无预览，回退成系统图标；宽高探测正常。
- **原因：** 该文件是 **8BPS 签名 + version=2** 的变体（规范本意 8BPS+1=PSD、8BPB+2=PSB，现实存在交叉）。代码按签名判定非 PSB，把 Layer & Mask 节的 8 字节长度字段误读为 4 字节，seek 错位后 compression 读到垃圾，解码失败。
- **解法：** PSB 结构判定改看**版本号**（version=2 → 8 字节长度字段），签名 8BPS/8BPB 均可；.psd 解码失败也兜底走 PSB 解析（反向变体同理）。
- **预防：** 解析二进制格式时，结构变体以"版本号 / 魔数 + 实测"为准，不轻信规范的组合枚举；新格式接入先用用户真实样本验证（构造数据测不出变体）。

## 011 vue-tsc 与 TypeScript 7（native）包布局不兼容

- **现象：** 执行 `npx vue-tsc --noEmit` 做类型检查，报错 `ERR_PACKAGE_PATH_NOT_EXPORTED: Package subpath './lib/tsc' is not defined by "exports" in typescript/package.json`。
- **原因：** 项目 TypeScript 为 7.x（native 重写版），包内导出布局与 vue-tsc 3.x 期望的 TS 5 布局不符；且 vue-tsc 未列入项目依赖。
- **解法：** 不引入 vue-tsc；类型验证继续靠 `pnpm build`（rolldown 转译）+ 编辑器语言服务，与阶段 1/2 一致。
- **预防：** 新会话勿再试 `npx vue-tsc`；待 TS 7 正式版 / vue-tsc 跟进适配后再评估纳入（阶段 6 打磨时复查）。

## 010 `mod core` 遮蔽内建 core crate

- **现象：** 数据层新增 `mod core;` 后编译报错：`core::ffi::c_void` 解析失败（cannot find `ffi` in `core`）。
- **原因：** crate 内声明与内建 core crate 同名的本地模块后，`core::` 路径优先解析为本地模块，原有指向内建 crate 的路径全部失效。
- **解法：** 该处改用 `std::ffi::c_void`（std 路径不受遮蔽影响）。
- **预防：** 顶层模块避免与内建 crate（core / std / alloc）同名；已同名时（本项目目录结构定为 `src-tauri/src/core/`），crate 内一律走 `std::` / `crate::` 显式路径。

## 009 长 dev 会话热更新状态损坏（界面渲染但交互全挂）

- **现象：** 连续几十次 HMR 后，界面看似正常渲染，但交互全部失效（按钮 / 拆分条 / 文件树无响应），部分数据（网格卡片）不显示——"半卡死"。两次复现。
- **原因：** vite + Vue SFC 高频全量重写后 HMR 状态链损坏（事件绑定与状态失同步），非业务代码 bug。
- **解法：** 重启 `pnpm tauri dev` 即恢复。
- **预防：** 大批量样式调整（数十次连续 HMR）后、或发现交互无响应时，直接重启 dev 再排查，先排除 HMR 损坏再怀疑代码；验收交互行为前建议重启一次 dev。

## 008 Figma 描边 inside 不占空间，CSS border 外扩占位

- **现象：** 按 Figma 标注的 padding 实现后，所有带边框容器的视觉间距都比设计稿宽 1~2px（如主窗口 padding 6 看着像 8）。
- **原因：** Figma 描边（stroke）默认 inside 对齐、不占布局空间，标注 padding 6 中有 2px 被描边占用；CSS `border` 在 padding 之外另占空间，`border 2px + padding 6px` 视觉就是 8px。每个带边框容器都差一个边框厚度。
- **解法：** 组件线条一律用 `box-shadow: inset 0 0 0 {宽}px {色}` 模拟（不占布局空间，与 Figma inside 描边逐像素一致）；hover/选中换色改 shadow 即可，还省掉了"透明边框占位防抖动"的 hack。
- **预防：** 已写入 `01_开发规范` 第 4 条——UI 组件禁止用 `border` 画设计线条，统一 inset box-shadow（真正分隔内容用的分割线另议）。

## 007 无边框窗口装饰四轮探索，终局为不透明 + 原生 DWM

- **现象：** 无边框窗口要阴影 / 圆角 / 1px 线框 / resize 判定，四轮方案全部翻过车：① window-shadows crate（1px 直角线框 + rwh 版本分裂）；② tauri `shadow: true` + DWM 抑制（主题边框 / DWM 圆角 / 顶边线 / 圆角外底色块，抑制不尽）；③ 全透明 + CSS 圆角阴影（当时判为终局）；④ 原生方案。
- **方案③ 同样翻车（用户实测四宗罪）：** inset 线框被三栏贴边背景遮住看不见；resize 判定双区域（阴影边缘 + 窗口边缘）；blur 40 超出 20px 阴影带被物理边缘裁成硬边；阴影带 20px 无法穿透点击到下层软件。
- **终局解法：** `transparent: false` + `shadow: true`（tao undecorated shadow）——Win11 DWM 圆角 8px 恰与设计一致、DWM 原生阴影（无硬边无阴影带）、resize 判定统一在物理 = 可视边缘（tao 只给顶边，四边用 `startResizeDragging` 热区补足）；mac 系统圆角 + 系统阴影；Win10 直角接受；线框用 `DWMWA_BORDER_COLOR` ≈ C4-15 合成色（Win11+）。
- **预防：** 桌面应用的窗口装饰（圆角 / 阴影 / 边框）优先用系统原生能力并按平台接受差异（Win11 8px / mac 系统 / Win10 直角），不要为追求跨平台像素一致去自绘——透明分层窗口与 DWM 的交互全是边角问题。

## 006 Figma 导出图标把示例文字转曲烘进 SVG
- **现象：** 文件夹卡片在 UI 上显示两组标题——动态渲染的标题之上还有一组固定的"新建文件夹 / 132 个子文件夹 / 1,321 个文件"。
- **原因：** `folder-card*.svg` 从 Figma 导出时，设计稿里的示例文字被转曲成 path 一并导出（viewBox 193×204 中含 42px 文字区）。
- **解法：** 剔除起始 y ≥ 160 的文字 path，viewBox 裁为 193×162 纯图标区；卡片标题/数量由组件动态渲染。
- **预防：** 图标类 SVG 导出前删除设计稿文字（或仅导出图标图层）；新增图标入库时检查 viewBox 与 path 数是否异常。

## 005 超大列表原生滚动拖拽必然闪白（棋盘格）

- **现象：** 10 万条列表拖拽原生滚动条，起步必闪一帧空白；加大 buffer、增量渲染、wheel 预渲染、同步渲染均只能缓解。
- **原因：** 浏览器对滚动条拖拽是合成器先行——拖块 1px 对应内容瞬移上千 px，主线程收到 scroll 事件时浏览器已画完一帧空白；且超大列表瞬移无 buffer 可覆盖（棋盘格）。
- **解法：** 自定义滚动——禁止原生滚动，wheel / 拖拽 / 键盘事件里先渲染目标区域、再用 transform 挪动画布，同一 JS 任务同一帧原子提交。实测完全不闪烁。
- **预防：** 主列表（内容展示区）滚动采用自定义 transform 方案，阶段 1 实现主窗口网格时直接沿用（原型见 `src/proto.ts`）。

## 004 OLE 拖拽放线程池导致无声失败

- **现象：** `drag::start_drag` 返回成功、状态显示"拖拽结束"，但目标位置没有文件。
- **原因：** 命令写成 async，被调度到线程池；Windows OLE 拖拽（DoDragDrop）必须在拥有窗口的主线程发起，线程池里拖拽被瞬间取消且无报错。
- **解法：** 改为同步命令（Tauri 同步命令运行于主线程），拖拽模态循环本身就是消息泵，实测拖出成功。
- **预防：** OLE / COM / 窗口消息类调用（拖拽、剪贴板、Shell）默认放主线程执行；确需后台执行时必须先验证行为。

## 002 `tauri dev` 一直 Waiting for frontend dev server

- **现象：** vite 显示 ready，Tauri 却反复 "Waiting for your frontend dev server to start"。
- **原因：** vite 默认把 dev server 绑到 IPv6 的 `::1`，而 Tauri 按 `127.0.0.1` 探测，localhost 解析不一致。
- **解法：** vite.config.ts 显式 `server.host = "127.0.0.1"` + `strictPort`，tauri.conf.json 的 devUrl 同步改为 `http://127.0.0.1:5173`。
- **预防：** 该项目配置已固化在 vite.config.ts / tauri.conf.json，新机器克隆即用。

## 003 vite watcher 监视 cargo 产物导致 EBUSY 崩溃

- **现象：** `tauri dev` 启动后 vite 崩溃：`Error: EBUSY: resource busy or locked, watch '.../src-tauri/target/debug/deps/app_lib.dll'`。
- **原因：** vite 的文件监视默认覆盖项目根目录，cargo 构建时改写并锁定 `src-tauri/target/**` 下的 dll，watcher 报错后杀死了 beforeDevCommand。
- **解法：** vite.config.ts 增加 `server.watch.ignored = ["**/src-tauri/**"]`。
- **预防：** 同上，配置已固化；新增前端目录时注意 watcher 排除范围。

## 001 PySide6 快速滚动卡顿（历史项目）

- **现象：** 虚拟缓存、懒加载都上了，快速拉动滚动条仍卡顿。
- **原因：** 疑为 QWidget 体系 CPU 光栅 + Python 侧绘制委托 + 滚动时同步解码/IO，并非单纯"没走 GPU"。
- **解法：** 本项目改用 Web 技术栈（浏览器合成器 GPU 加速，createImageBitmap 离线程解码）。
- **预防：** 已写入 01_开发规范 第 7 条——列表虚拟化、异步解码、布局预计算（用 metadata 宽高）、滚动降级（主色占位）。验收线：10 万资源快拖不掉帧。

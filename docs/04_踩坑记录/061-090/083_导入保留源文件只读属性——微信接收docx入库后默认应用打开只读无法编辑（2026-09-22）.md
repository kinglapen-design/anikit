# 083 导入保留源文件只读属性——微信接收的 docx 入库后默认应用打开只读无法编辑（2026-09-22）

## 现象

docx 导入 AniKit 后，库里「默认应用打开」（WPS / Word）标题栏只读、无法编辑保存；文件属性对话框「只读」勾选为真。用户判定：导入后文件变成了只读。

## 排查与原因

全库扫描（`Get-ChildItem -Recurse | Where IsReadOnly`）：2142 个文件中**仅 4 个只读，且全是同一批「穿越异世界剧本」docx**——不是导入管线普遍设只读，而是这批源文件本身带只读属性（微信 / QQ PC 版接收文件的著名行为：接收目录内文件自动置只读防误改），导入时被原样保留：

- `services/import.rs` `store_file` 的 Copy 分支 = `fs::copy`，Windows 上即 CopyFileExW，**保留源文件属性（含只读位）**；Move 分支 = `fs::rename`，属性和 ADS 全保留。两条入库路径都没有属性清洗步骤。
- 只读位平时无害（删除 / 重命名走目录项操作不受影响），只在「写内容」场景炸：外部编辑器回写（docx）、APP 内 txt 编辑保存（`write_text_asset` 会报「保存失败：拒绝访问」）。

排除项：无 MOTW（Zone.Identifier ADS 不存在，非 Word 保护视图）；ACL 正常；后端无持有句柄。

## 解法

`store_file` 落库后剥只读位（`clear_readonly`：读 metadata 判 `permissions().readonly()`，置位才 `set_readonly(false)`，失败不阻断导入）——**入库即归库管**，库内文件不该被源属性卡住写路径。单测 `store_file_strips_readonly_attr` 覆盖 Copy / Move 两分支。存量 4 个只读文件已用 PowerShell 批量解锁。

## 预防

- 文件「复制」在 Windows 不等于「新建一份干净副本」：CopyFile 系 API 保留属性 / 时间戳，做素材池 / 沙箱类收纳时要显式决定属性口径（本库 = 剥只读，其余属性不管）。
- 用户报「导入后变成 X」先对比源文件与库内文件的 X 是否一致——归因方向（导入添加 vs 源继承）决定修管线还是修认知。
- 微信 / QQ / 邮箱客户端接收目录是只读属性的高发源，中文办公素材场景必遇。

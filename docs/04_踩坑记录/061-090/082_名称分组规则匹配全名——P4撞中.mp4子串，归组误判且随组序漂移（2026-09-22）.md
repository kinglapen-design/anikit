# 082 名称分组规则匹配全名——"P4" 撞中 ".mp4" 子串，归组误判且随组序漂移（2026-09-22）

## 现象

文件夹分组：P3 / P4 / P5 三组同为「扩展名 mp4 + 名称分词 P3/P4/P5」，P5A_01.mp4 却归进 P4 组（P4 / 9）；把 P5 组上移到 P4 之上后它才归 P5——**归组结果依赖组的排列顺序**。

## 原因

归组名称规则（`src/lib/grouping.ts` `ruleHits` name 分支）对**含扩展名的完整显示名**做子串匹配：`"p5a_01.mp4".includes("p4") === true`——"p4" 撞中的是扩展名 ".mp4" 里的 "mp4"。于是 P5A_01.mp4 同时 AND 命中 P4 组（ext 1 + name 1 = 2）与 P5 组（同为 2），权重平局按定义顺序先建者优先 → P4 在前归 P4。P3_01.mp4 同样命中 P4 组，只是 P3 组排最前把它"救"了下来，所以只有 P5 露馅。同类雷：任何「字母+数字」分词都可能撞上数字结尾的扩展名（"P3" ⊂ ".mp3"、"J4" ⊂ ".mj4"……）。

9-17 的「命中关键字更多者」修订（P1 vs P1_2K 案）治的是词数不同的平局，治不了本坑——两案同根：**匹配对象本就不该含扩展名**，扩展名归属有专门的「扩展名」规则。

## 解法

名称规则匹配改对**词干**（`nameStem`：去最后一个 "." 后缀；点开头 / 无点取全名）：`ruleHits` 与 `ruleWeight` 的 name 分支同步换。修后 P5A_01.mp4 唯一命中 P5 组，归组与组序脱钩；P1_02_2K 案成果不回退（"2k" 在词干内真命中）。PRD 02_文件整理/04_分组「自定义规则」已补口径。

## 预防

- 对文件名做子串 / 包含匹配时先问一句：目标是词干还是全名？默认应锁词干（批量重命名早已是词干口径——「规则只作用词干，扩展名不动」）。
- 「平局按顺序」类裁决会把数据 bug 伪装成顺序 bug：看到「换序才好使」要立刻怀疑双方都命中了，而不是顺序逻辑本身。

## 075 ffprobe 探测分流把本可直解的 HEVC 送进软编码转码——试播回退优于探测预判（2026-09-13）

- **现象：** 用户实机：一批 HEVC 编码的 MP4（无限盲盒，1080p30 约 190MB/条），悬停 / 点开要等几十秒「转码中」，每次打开软件 CPU 长时间满载；同一批文件在 Eagle 里导入即看、悬停哪个看哪个。
- **原因：** `get_media_source` 用 ffprobe 探测编码做直渲 / 转码分流，白名单只认 h264 + aac/mp3——HEVC 一律判转码，走 libopenh264 软编码全量重编码（分钟级纯 CPU）；产物又放在 cache/tmp 属开库清空名单，每会话重转。实际上 WebView2（Chromium）经 Windows Media Foundation 可直解 HEVC（OS 装了解码器即可，多数 Win10/11 机器自带或厂商预装）——Eagle 能播即证明本机有此能力。探测分流对「webview 到底能播什么」的静态预判，比平台真实能力保守且每次调用都要付 ffprobe 成本。
- **解法：** 直读优先 + 播放错误回退：一律先直给源文件路径（零探测零等待），前端四个播放点（HoverVideoLayer / HoverAudioLayer / previewMedia / TabLinks）在 `<video>`/`<audio>` error 后带 `forceTranscode` 重调，后端才转码兜底；转码产物迁 cache/media 跨会话保留（stamp 校验源变化重转），每资产终身只转一次。
- **预防：** 判断「能不能播 / 能不能渲染」优先用**真实试跑 + 错误回退**，不要用静态白名单预判——白名单永远落后于平台真实能力（OS 解码器、GPU、运行时版本差异），且预判本身（ffprobe）也是成本。缓存产物清空前先评估重建成本：秒级重建（波形 / 帧条）可会话级清空防膨胀，分钟级（转码）必须持久 + 失效校验（stamp），别把「防容量膨胀」做成「每会话重做分钟级重活」。

# 122 越界后才发起 OLE——快速松手错过系统接管，形成拖拽即接管 + 窗内原生事件续接（2026-11-04）

## 现象

素材跨窗口拖到剪映时，随手快速一拖一送经常没有落入，刻意放慢才成功。用户两段录像均为第一次快速手势失败、第二次慢拖成功，容易被误判为目标软件导入慢或偶发丢文件。

## 原因

旧前端在卡片移动超过 6px 后只建立应用内 pointer 拖拽，直到 `pointermove` 报告指针越出窗口，才调用 Tauri 命令。命令经异步 IPC 到主线程后才执行 `DoDragDrop`，而 Windows 只有在该模态循环内才持续接管按键与落窗。

快速松手时，最后收到的可能是窗内 move 或窗外 pointerup，OLE 尚未来得及启动；`drag` crate 的 `IDropSource::QueryContinueDrag` 看到左键已松开会直接结束，目标软件不会收到 CF_HDROP。旧探针只断言越界时调用过命令，覆盖不到真实按键时机，因此全绿也证明不了快速手势可用。

## 解法

文件卡形成拖拽即提前发起 OLE，把系统接管点从「越出窗口」前移到「移动超过 6px」。本窗 Wry `enter / over` 继续驱动原应用内落点引擎；真实 `DoDragDrop` 结果返回后，再决定执行窗内落点还是结束跨窗口拖拽。

`drag_assets` / `ws_drag_paths` 返回 `dropped`、客户区物理坐标和 Ctrl 实态。前端先除 `devicePixelRatio` 再做窗内外与落点判定；曾出窗再返回仍取消且不回导，Ctrl 建链接保持原语义。

## 预防

- 涉及系统接管的三段式手势，必须验证「快速移动并立即松手」，不能只验证命令是否最终调用；慢拖通过不代表竞态不存在。
- 原生模态拖拽会改变 pointer 事件的到达时机，窗内业务需要显式续接原生 enter / over / drop 结果，不能假设 pointermove / pointerup 顺序不变。
- 系统回调坐标与 DOM 坐标必须标明物理 / CSS 单位；物理像素进 `elementFromPoint` 或窗口边界判断前统一除 `devicePixelRatio`。
- 本轮编译与构建通过，真实快速拖放由用户接管验收，未以自动化探针的未完成结果冒充实机通过。

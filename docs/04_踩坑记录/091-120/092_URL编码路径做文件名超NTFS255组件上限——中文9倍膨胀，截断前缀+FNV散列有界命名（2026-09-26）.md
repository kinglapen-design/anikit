# 092. URL 编码路径做文件名超 NTFS 255 组件上限——中文 9 倍膨胀（2026-09-26）

## 现象

工作空间（ws）部分音频 / 视频缩略图生成失败：`ws_thumb_queue` WARN「工作空间缩略图生成失败（记入失败记忆）」，条目落回格式图标。规律 = **中文长路径必败、同目录 ASCII 短名成功**；ffmpeg / ffprobe 单独跑这些文件全部正常——解码链路无辜。

## 原因

ws 缩略图 / peaks 缓存文件名 = `encode_rel(rel)`（整条相对路径 URL 编码）+ `-{mtime}-{size}.{ext}`。URL 编码下**一个中文字符 = 3 字节 UTF-8 → %XX × 3 = 9 个文件名字符**，深中文 rel 编码后轻松爆炸：实锤案例 `02_创作/01_原创动画/01_计划中/224/01_灵感/05_音乐/不要去看天气预报.wav` 编码后整名 **257 字符**，超 **NTFS 单路径组件 255 字符上限**，`fs::write` 报 Invalid argument → `generate_thumb` 的 `.ok()?` 静默 None → 记入失败记忆。

python 实锤两点：① 同路径直接写即失败，与 AniKit 无关；② **加 `\\?\` 长路径前缀也救不了**——前缀绕的是整条路径 260 的 MAX_PATH 限制，255 是**单个路径组件（文件名）**的硬上限，组件级限制无解。

## 解法

缓存键改**有界命名**（`workspace.rs::job_key`，缩略图 / exe 图标 / peaks / 失败记忆 / 队列去重共用）：

``` text
{截断≤80的 encode_rel 前缀}-{fnv64hex(rel)}-{mtime_ms}-{size}.{ext}
```

- 前缀只截在完整 %XX 转义边界（不切半），只供人读；
- 唯一性由 **FNV-1a 64bit**（手写十几行，不加依赖；不用 DefaultHasher——跨工具链版本结果不稳定）hex 16 字符兜底，不同 rel 不撞名；
- 全长 ≤ 80+1+16+1+21+1+20+扩展名 ≈ 150 字符，离 255 留足余量；mtime+size 仍内嵌判新鲜。
- `purge_stale` 由「编码前缀 starts_with」改**按 hash 段 `-{fnv64hex(rel)}-` contains 匹配**（截断前缀不再唯一，hash 段才是身份；按扩展名的格式图标无此段天然不受影响）。

**存量迁移**：旧命名缓存全部失效成孤儿。thumbs / peaks 是纯缓存可删可重建，`.anikit/cache_v2` 标志文件记一次性清理——开空间（activate_space，start_watch 前）标志不存在则清空 thumbs/ 与 peaks/ 后落标志；失败记忆是进程级不落盘，无需迁移。

## 预防

- **凡「路径 / 用户文本 → 落盘文件名」的转换，先问长度上界是什么**——URL 编码、hex、base64 对非 ASCII 都有倍数膨胀（URL 编码中文 ×9），文件名场景必须截断 + 散列兜底唯一性，不能指望输入够短。
- Windows 文件名限制两层：整条路径 260（`\\?\` 可绕）与**单组件 255（无解）**——测长文件名场景要盯组件长度，别只盯总长。
- 缓存键设计三要件互相牵制：可读（前缀）/ 唯一（散列）/ 新鲜（内嵌实况）——动了命名就必须同步 purge 匹配口径与存量迁移，缺一即留孤儿或误清。

# 可见序与存储序脱钩期落点必物化——新增区置顶钉住期间拖拽排序「提示成功但没用」（2026-10-13）

## 现象

链接文件与原始文件同在一个文件夹（撞键双位置）时，把链接卡片拖到目标间隙，toast「已调整顺序」正常弹出、撤销也在，但卡片在网格里纹丝不动；切换到别的目录再切回来，顺序变成拖后的样子，再拖又一切正常。同形态报错本月前还有两例：树名称排序下拖文件夹「显示排序成功但实际没有执行」（08-14）、素材显示排序下拖拽被排序键盖回（08-19）。

## 原因

三例同根：**显示层存在重排机制时，可见序 ≠ 存储序，而落点类写操作按存储序执行**。本例的重排机制 = 新增区置顶（`newArrivals`：链接粘贴 / 导入 / 新建时按 `assetId|folderId` 基底键登记，命中项集中钉在段首，切视图 / 切库 / 物化才归位清空）。置顶钉住期间，自定义排序分支的拖拽落点仍按存储序发 `reorder_placements(items, beforeItem)`：

- 拖 pinned 项：可见间隙与它实际的存储邻位对不上，存储侧重排可能是**无操作**（本就插在它已在的存储位置）；
- 即便存储真动了，`runOp` 全量 refresh 后显示层仍按置顶钉回段首，用户看不到任何变化；
- 基底键不区分同夹多条位置，origin + 链接同夹时**两条都被钉**，相对顺序也被锁死——用户报的「同夹必现」即此；
- 切目录触发 `clearArrivals` 归位，存储序（此前已写对）浮出显示，于是「又好了」——自愈假象掩盖了病灶，定位走了弯路。

## 解法

收进既有物化分支（显示排序物化同款，单写点 `dropAssetsGap`）：目标段可见清单含 pinned 项即把该层**可见序（含置顶段）物化为存储序**、拖拽组按落点并入整层重写（全层序列 + 段尾锚点），落笔后 `clearArrivals` 归位——pinned 位置由自定义序承接，所见即所得；无 pinned 的常态路径零变化。判定用「目标段可见清单是否含 pinned 项」而非全局 Map 非空，避免无关文件夹的置顶被无辜归位。

## 预防

- **新增任何显示层重排机制（排序键 / 置顶钉 / 过滤）时，落点类写操作（拖拽排序 / 插入）必须同轮评估脱钩**：可见序 ≠ 存储序期间，一律物化可见序整层重写，禁止按存储序插单项——物化分支已立三例先例，第四起应先查本坑。
- 「提示成功但界面没动、切视图又好了」= 显示层钉住 / 盖回的典型信号，排查先找会话级显示态（排序键、arrivals、过滤），别先怀疑后端没写盘。
- 反向对照探针（stash 修复复现病灶）是坐实「显示层盖回」类根因的最快手段，本例正向反向各一遍即闭环。

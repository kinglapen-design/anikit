# 踩坑 109：headless 按需出帧模式 rAF 整段停摆——「等一帧」工具代码探针语境一律定时器（2026-10-10）

**错误信号**：md 分屏 typewriter 跟滚在探针里完全不滚（scrollTop 恒 0），功能代码与断言全部正确；同探针早前版本（textarea 内核）同机制却绿——迷惑性极强。

## 根因

headless Chromium（`--headless=new`）的帧生产是**按需模式**：有视觉损伤（DOM 变更 / 截图）才产帧，空闲窗口期不出帧。rAF 回调绑帧生产——**没帧就永不回调**。分屏 typewriter 用 rAF 做合一节流，守卫变量存 rAF id：回调不达 → id 不归零 → 守卫永锁，后续所有调用被早退，且新注册的 rAF 同样饿死（实证：cancel 重排后 runs 仍 0）。CSS 过渡同族受害——类已翻转、computed 样式冻在过渡起点（H 段 Checkbox `bg` 恒为品牌色之谜）。

真机（headed）帧源不断，无此问题；纯探针 / headless 语境病。

## 正解

「等一帧再算」的合一 / 节流一律 `setTimeout`（16ms ≈ 一帧），不用 rAF——定时器不依赖帧生产（PreviewText.scheduleSplitScroll）。**「过会儿解锁」的锁改墙钟截止时刻**（`linkLockUntil = performance.now() + 100`）：计数 + 定时器解锁在节流环境同样冻死（解锁回调迟数秒、联动长锁全瘫，探针 O 联动段实锤），墙钟到点自然失效、零回调依赖。探针断言同步放松：跟滚收敛轮询确定性效应（右栏滚到底——只有定时器能写），不写死 sleep、不看「本来就 0」假收敛；过渡终态只断言类不读 computed。

## 预防

- 写「下一帧再处理」逻辑前先想运行语境：工具函数若会被探针 / headless 驱动，直接定时器；
- 任何「靠回调复位」的守卫 / 锁（rAF id、setTimeout 解锁）一旦回调失约即永久卡死——要么取消-重排自愈，要么墙钟截止；
- 探针里涉及滚动 / 过渡终态的断言，先怀疑帧生产与定时器节流，别当功能 bug 修。

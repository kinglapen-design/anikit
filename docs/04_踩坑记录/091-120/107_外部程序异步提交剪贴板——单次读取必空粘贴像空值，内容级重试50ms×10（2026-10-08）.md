# 外部程序异步提交剪贴板——单次读取在内容到达前必空（2026-10-08）

## 现象

外部复制一张图片（截图工具 / 浏览器），马上 Ctrl+V 粘贴进 APP「像空值」——什么都没发生；稍等几百毫秒再粘就成功。偶发性强、越急越中。

## 原因

`import_clipboard` 在按键瞬间**单次**读系统剪贴板（图片 → 文件列表 → 文本三路）。但外部程序写剪贴板普遍是异步的：截图工具先走 UI 动画再提交位图，浏览器复制大图要先编码再落 PNG/DIB。用户感知「复制完了」到剪贴板里真正有内容之间存在几十到几百毫秒窗口，单次读在这个窗口内必空。空读报错后被前端「剪贴板无图无文件属常态」的静默降级口径吞掉，于是表现成「没反应」。

开剪贴板竞争的重试（3×50ms）只防「被占用」，不防「内容还没到」——OpenClipboard 成功 ≠ 数据已提交。

## 解法

内容级重试：三路皆空时不立即报错，按 50ms 间隔重读、最多 10 次（最长等 500ms）；任何一路有内容（含不可导入的纯文本）即停——有内容 = 写入方已提交完毕，再等无意义。覆盖异步提交窗口后，「复制即粘」一次成功。

## 预防

- **读系统剪贴板不能假设「复制动作完成 = 内容已就位」**：面向外部写入方的读取（剪贴板 / 拖拽 / 文件监听同类）都要按「内容可能晚到」设计——要么内容级重试，要么监听变更通知驱动，单次读只配用于纯内部状态。
- 静默降级口径会掩盖时序类故障：排「偶发没反应」先怀疑竞态，再看降级路径是不是把报错吃了。
- cargo 的 `.cargo/config.toml` 按**工作目录**发现、不看 `--manifest-path`：本项目 cargo 命令必须在 `src-tauri/` 下跑，否则 `FFMPEG_DIR` / `LIBCLANG_PATH` 丢失，ffmpeg-sys-next 回落 pkg-config 报构建错。

# 099 RDC 递归监听不穿透 junction——链接子树事件零上报，每链接目标单独补监听 + 路径翻译（2026-10-02）

- **现象：** 工作空间方向 b（外部文件夹 junction 挂进 WS 子目录）spike 实测：在 junction 链接子树内新建 / 改名 / 删除文件，工作空间主监听（notify Windows 后端 RDC 递归监听 workspace 根）**收不到任何事件**——3 秒观察窗口 0 条。链接目录内的外部改动在 APP 里完全不热刷新，与「双向热刷新」承诺直接冲突。
- **根因链：** Windows ReadDirectoryChangesW 的递归监听沿真实目录树向下走，junction 是 reparse point「门」不是真实子目录——**RDC 不穿透门**，门后目标子树的变更不在监听根的变更流里。notify 8.2 Windows 后端对此无特殊处理也无任何事件标志，静默漏报（区别于缓冲区溢出尚有 `ERROR_NOTIFY_ENUM_DIR` 可查——见待办 2026-10-01 观察项）。这是 RDC 机制本身的行为而非 notify 的 bug：Explorer / Everything 对 junction 子树同样按真实目标路径处理（ws 搜索立项的 junction 路径映射需求同源）。
- **解法：** spike 定案（`adapters/junction.rs` 三个 #[ignore] 测试，`cargo test spike -- --ignored` 可复跑）后按「每条链接单独补监听」落地：主监听照旧管 workspace 根本体；每条「链接在且目标在」的登记链接单独对 **target** 起 watcher（AppState.workspace 槽位改 Vec），事件路径从 target 前缀**翻译回词法门路径** 后走同一 `changed_dirs` / 回声消重 / 前端精准重扫管道——前端零感知。链接拓扑变化（增 / 删 / 重指 / 改名 / 移动 / 剪切粘贴）后命令层**恒整体重建监听**（简单口径，不做 watcher 集增量维护）；断链链接不补监听（目标不在无可监），重指修复后随重建恢复。
- **预防：** ①**凡是监听含 reparse point（junction / symlink）的目录树，默认递归监听不穿透**——落地前先 spike 验证穿透性，不假设；需要门后事件就每条链接单独补监听 + 路径翻译，别指望主监听兜住。②监听类功能验收必须含「链接子树内改动 → UI 热刷新」用例（已入 `tools/cdp-ws-link-probe.py` 回归）。③路径翻译坚持「词法门路径」口径：fs 操作与缓存键都打在门上（链接目标保持干净），事件翻译与路径闸（`resolve_under` 命中登记链接返回词法路径）同口径才不自相矛盾。

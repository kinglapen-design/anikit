# Everything 查询串整体加引号 = 短语字面搜索——修饰符/path: 作用域全失效（2026-10-03）

## 现象

工作空间搜索 Everything IPC 探针（`tools/everything-ipc-probe.py`）：裸词 `vite` 正常命中 430 条，但 `ext:ts`、`path:"E:\..."`、`folder:wfn:"..."`、`parent:` 等**一切带冒号的修饰符查询全部 0 命中**——连 Windhawk better-file-sizes 生产环境在用的 `folder:wfn:"<path>"` 形态都零命中。同字符串在 Everything GUI 里 42 条命中；官方 DLL（Everything64.dll）同串也 42 条。实例、索引、协议帧全部排除后，真凶是**探针自己给搜索串整体套了双引号**（`search = f'"{term}"'`）——Everything 里双引号 = 短语字面搜索，引号内 `ext:` / `path:` 全被当普通文本，自然零命中；裸词加引号不受影响（`"vite"` 与 `vite` 等价），通配符 `*` 在引号内居然仍生效，迷惑性拉满。

## 原因

排障被两个巧合带偏：①裸词与通配符在引号内行为正常，只有修饰符死——现象恰好伪装成「IPC 不解析修饰符」；②早期测试把引号写死在探针里，所有后续变量（search_flags / 版本 / 权限）都在错误的基准线上排除。GUI 对照 + DLL 对照二分后才锁定差异只剩「字符串本身」。

## 解法

**Everything 查询串原样透传，绝不整体加引号**；`path:"<目录>"` 的引号只包路径参数（防空格断词），关键字部分原样。Rust 适配器（`adapters/everything.rs`）与服务层（`services/ws_search.rs` 查询构建）头注均已写明本条。

## 预防

- 搜索 / 查询语言类集成（Everything / SQL / Lucene）：**先验证「最小修饰符查询」再验证裸词**——裸词在任何转义形态下都可能蒙混过关，修饰符才是解析器形态的试金石。
- 对照实验要控制到「只剩一个变量」：本坑_GUI 与 DLL 都正常_早就把嫌疑锁死在自写代码，却先怀疑了协议与实例一整轮——对照组正常时，差异只可能在自己发出的字节里。
- 探针 / 测试脚手架里的「为了方便加的引号 / 转义」是污染基准的高危动作，写入探针注释备查。

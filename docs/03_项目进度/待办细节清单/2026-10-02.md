## 立项（2026-10-02 用户定，下个会话做）：工作空间搜索 = Everything 手写 IPC + 自研爬盘回退

PRD 02 步骤 3「搜索搁置」条解冻。2026-10-02 咨询轮调研后用户拍板（过程见开发日志 [2026-10-02_15](../../02_开发日志/2026-10/2026-10-02_15_工作空间搜索方案定案.md)）：**Everything 手写 IPC 集成为主、自研爬盘回退兜底，不押 Windows Search**。用户判断原话：大部分 Windows 用户基本人手一个 Everything；存了很多项目和素材的（目标用户），没有的大概率也不用电脑工作而是日常使用。

### 双层架构定案

- **Everything 层（探测到即全功能）**：搜索 + 文件夹数量标记都走它。
- **自研爬盘回退层（无 Everything）**：搜索降级为 Enter 触发的慢速遍历搜索（流式 + 进度 + 可取消），不做成即时搜索冒充；数量标记维持现状（仅已加载目录的直接文件数，不递归补——大目录树常驻递归探测烧 IO/CPU 是 2026-09-19 砍掉的方案）。
- **明确不依赖 Windows Search**：其索引默认只覆盖用户配置文件夹 / 库，工作空间是任意盘任意路径大概率不在索引里——OLE DB（Search.CollatorDSO）查未索引路径直接返回空，WinRT StorageFolder 查询退化为同款爬盘还多一层 COM 开销；也不编程爬索引 scope（ISearchCrawlScopeManager 会引入 SearchIndexer 资源占用骂名）。`search-ms:` 协议可作右键「在资源管理器中搜索」顺手项（十行代码），不属本批。

### Everything 层技术要点

1. **手写 IPC，不引 DLL、不用 es.exe**。Everything64.dll 只是 IPC wrapper 且再分发条款不明；es.exe 每次查询起进程，不适合批量计数场景。协议直接手写：1.4 = `FindWindow("EVERYTHING_TASKBAR_NOTIFICATION")` + WM_COPYDATA（EVERYTHING_IPC_QUERY2 + 自建 message-only 接收窗等回复，超时降级）；项目已有 `windows = "0.62"` 与 shell_menu / clipboard 等手写 Win32 先例。现成参照 = Windhawk better-file-sizes 模块（纯 Win32 实现「Everything 查文件夹大小」，含 SDK3 / legacy 双模式与 reparse point 处理）。
2. **能力探测降级**（ffmpeg sidecar 范式）：探测不到运行中的 Everything → 搜索走回退层、计数回落现状，主功能零影响。区分三态：「未安装」走引导页推荐；「已安装未运行」可代拉起（启动用户自己的软件无授权问题）；「运行中」全功能。
3. **搜索口径**：`path:"<ws根>"` + 空格分词（Everything 原生 AND），仅命中文件名与路径（PRD 03 口径）；结果全路径映射为 ws rel 喂现有视口过滤链。**junction 目标根须分别查询再映射回 rel**——Everything 对 reparse point 子树按真实目标路径建档（junction 路径下查不到），与方向 b（待办 2026-10-01 B 节）共享同一张「目标前缀 ↔ 链接 rel」映射表，两者宜同期设计。
4. **文件夹数量标记 = 一次性聚合为主**：开空间 / 手动刷新发一条 `path:root` 全量查询（10 万条约 10–20MB 一次 IPC 拷贝），Rust 内存沿路径向上聚合出每个文件夹的直接文件数 / 递归总数；增量 = 挂现有 workspace-fs-changed 链对变更目录发窄查询修正。回填 TreeRowItem 现成 count / directCount 双口径渲染位（WsEntry 加字段或旁挂 Map 实施时定）。
5. **工程纪律**：同步 IPC 一律 spawn_blocking（踩坑 074）；Everything 返回路径进 Shell 链前注意 `\\?\` 前缀形态（踩坑 078）与超长中文路径（092）；notify RDC 溢出盲区（待办 2026-10-01 观察项）可用定期窄查询兜底。
6. **二期增强（非本批）**：探测到 Everything 1.5 实例则升级 SDK3 命名管道（持久连接、实测快至 20 倍、原生 GET_FOLDER_SIZE 命令、index journal 可补 notify 溢出盲区）。

### 回退层（自研爬盘）技术要点

Enter 触发（不跟 150ms 去抖即时搜索混），递归 `read_dir` + rayon 并行 + 可取消令牌，命中流式回前端并显示「已扫 N 个文件」进度；匹配 = 文件名 / 路径子串（与库搜索分词语义一致）；跳过 `.anikit`。速度预期 ≈ 或优于资源管理器绿条（其爬取单线程），且行为全机型均匀——这是它优于 WinRT 查询路线的点。

## 立项候选（2026-10-02 用户实机走查链接功能时定方向）：从 WS 里「链出去」——WS 内建真实文件夹 + 外部入口 junction

用户在方向 b 实机走查后明确了链接的完整产品哲学：**链接是双向的**。以 01_projects 为例——它既可以是外部目录 junction 挂进 WS（方向 b，已落地），也应该可以反过来：在 WS 里建真实文件夹、把入口 junction 摆到外部常用位置（方向 a′ 的产品化，此前仅作零代码推荐用法存在）。用户视角两种摆法就是「两个一样的文件夹」，内容只有一份。

**从 WS 里链出去的硬价值（用户原话要点）**：库里硬链接的素材都落在同一储存空间——文件夹本体留在 WS（空间卷）里，硬链接落盘「想跨盘符都不给机会」。即内容物理留在储存空间卷 = 阶段九硬链接永不触发跨卷回退（同卷成 / 异卷败的交汇问题从根上消失）；摆在外部的入口 junction 只是门，误删十秒重建，内容零风险。

实施要点（开工时细化）：入口 junction 的落点选择（系统目录选择器，复用方向 b 链路）；入口的生命周期口径 = **只管创建不管存续**——内容本体在 WS 内已被 watcher 覆盖，外部门被删不伤分毫（方向 b 的断链标记体系只管得进 WS 内的门，管不到 root 外的入口，也无需管）；与阶段九硬链接批次一同定稿落盘口径。

**嵌套兼容性结论（2026-10-02 用户问，已答无需砍方向）**：链出去与链进来可以共存——门套门由 NTFS 连续替换解析（外门先进 WS 内目录、内门再穿到方向 b 目标），内容永远只在最终目标一处，从哪个门进都是同一份。APP 看不见 root 外的入口门（登记清单 / 路径闸 / 缓存键全锚 WS 内词法 rel，无感）；热刷新双路皆通——经外门改普通内容走主 watcher（物理写在 WS 内），经外门改内层链接内容走方向 b 的目标补监听（物理写在目标盘，翻译回内层 rel 精准重扫）；断链各自独立（外门没 = 十秒重建，内门断 = 置灰重指）。唯一红线 = **用户手动 mklink 把门指成环**（外门指 WS 内目录、WS 内再建门指回外门子树）会让递归复制 / 遍历打转（资源管理器同样如此）——APP 内建链接的防循环校验只覆盖「挂进 WS」方向，root 外的门管不到，属用户自造场景不防。

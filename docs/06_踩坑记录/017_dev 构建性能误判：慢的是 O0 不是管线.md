## 017 dev 构建性能误判：慢的是 O0 不是管线

- **现象：** dev 模式（`pnpm tauri dev`，cargo debug 构建）下动图帧条 18 帧要 5-10 秒、CPU 风扇猛转；序列帧 17 张"秒读"。排查方向一度以为是架构问题（帧条反复解析 GIF / 等解包 / 大图二次解码）。
- **原因：** 纯 debug（opt-level 0）的图像解码 / 重采样比 release 慢 10-30 倍，基准实测 1080p webp 帧条 O0 = 725ms/帧 vs release = 43ms。两层叠加：① 依赖 crate 内的解码（webp 解码 455ms）；② **泛型函数在调用方单态化**——imageops::resize 的代码生成在我们 crate（O0）而非 image crate，只给依赖开优化管不到它（261ms）。序列帧"秒读"只是因为 PNG 小图基数小。
- **解法：** Cargo.toml `[profile.dev] opt-level = 1`（管泛型单态化）+ `[profile.dev.package."*"] opt-level = 2`（管依赖内部代码），效果 725→57ms/帧，与 release 同量级；依赖只编一次，日常增量构建不受影响。
- **预防：** dev 模式下任何"慢"的结论先隔离构建配置变量——性能判定以 release（或 O2 基准）为准，优化需求先在 release 复测再立项；dev 优化配置已固化 Cargo.toml（图像基准 thumbnail.rs bench_frame_strip_stages #[ignore] 可复跑）。

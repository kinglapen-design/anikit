## 01. 模块化

动画软件数量繁多，我们不可能适配所有软件，需要开发时就要抽象成接口，方便其他人自己对接插件，也方便我们后续自己加入软件的对接。

- **统一通信通道：** AniKit 内置本地 WebSocket 服务，各软件插件（适配器）连接后与 AniKit 双向通信：AniKit 下发指令（打开文件、导出、发送至舞台），插件回传进度与结果。第三方可按接口文档自写适配器。
- **能力分级：** WebSocket 通道本身通用，能否深度对接取决于各软件的脚本 API——Blender（Python/bpy）、Toonboom Harmony（脚本 API）、Moho（Lua）等可完整双向对接；CSP、CTA 等无开放自动化 API 的软件无法深度对接，以"约定文件夹 + 文件监听"弱集成兜底。各软件具体能力在架构阶段逐一验证。
- **引擎风险预留：** Animate 目前仍是 CEP 插件体系，但 Adobe 整体在向 UXP 迁移，适配器层需预留更换插件引擎的可能。
- **AE 预留：** AE 可用 `AfterFX -r 脚本.jsx` 执行自动化脚本、aerender 命令行渲染预览，后续按同一适配器接口接入。

以下都以 Animate 为案例，我自己常用的就是 Animate 和 AE，MVP 先跑通 Animate，让我可以快速应用在工作中，测试软件。

## 02. 缩略图生成

识别所有没有伴生图的 fla（metadata 中无缩略图记录），列出来后，一键导出，可视化导出进度；支持暂停 / 取消，失败项列入列表可重试；Animate 同一时间只能开一个实例，任务串行执行。

#### 1. 技术路线

矢量图形与时间轴动画必须由 Animate 渲染，无法完全绕过（fla 本质是 XFL 压缩包，只能提取内嵌位图当作兜底预览，不能渲染元件与动画）。驱动方式有两种：

1. **免插件兜底（jsfl 直启）：** AniKit 生成临时 .jsfl 脚本（打开 fla → 逐帧导出 PNG → 关闭不保存），直接用 Animate 打开该脚本即自动执行；脚本把进度写入日志文件，AniKit 轮询读取。优点：用户零安装；缺点：Animate 窗口会闪动。
2. **CEP 插件通道：** 插件在线时走 WebSocket 下发指令，进度实时回传、不闪窗，体验最佳。

PNG 序列帧由后端合成动态 WEBP（ffmpeg / sharp），存放为 info 文件夹内的伴生缩略图。

#### 2. 居中与裁剪策略

导出的图像是否居中完整，分三种情况处理：

1. **内容在舞台内但未居中（大多数）：** 不移动任何内容，原样导出后按内容包围盒**自动裁剪居中**（trim），再缩放至缩略图尺寸。避开"记录坐标 - 移动 - 还原"的脆弱链路，零风险。
2. **内容在舞台外被裁剪：** 自动方案只能"记录初始坐标和缩放 → 缩放位移至舞台中央 → 导出 → 还原坐标（保持用户原坐标，只在生成缩略图时临时移动）"，且仅对单元件、动画在元件内的情况可靠。
3. **主舞台多帧多元件的复杂时间轴：** 自动方案脆弱易出 BUG，不做。由用户在插件中手动导出缩略图兜底（见 03，用户自行调整画面后导出，无需自动对齐），手动但 100% 可靠。

由我们插件导出的 fla 天然保持坐标 / 已对齐，自动缩略图效果最佳，形成正向循环。

## 03. 软件插件

先做 Animate 的 CEP 插件，通过本地 WebSocket 与 AniKit 通信。

插件功能：
- 全局选项：导出静态缩略图，导出动态缩略图。
- 导出为新的文件，并生成缩略图：
	- 单选：导出为 fla。
	- 多选：导出为单一 fla；将所选项分别导出 fla。
	- 导出选中帧为新文件：若用户选中的是一串动画帧而非元件，则直接剪切粘贴帧后导出序列，不做缩放对齐舞台中央。
	- 对齐方式：保持坐标、对齐至舞台中央；多选元件或元素时，识别整个多选后的外边框（联合包围盒），先记录各元素坐标，再整体缩放对齐至舞台中央，导出后逐一还原。
- 导出缩略图（即手动兜底，无需自动对齐——用户选择直接导出，大概率是已自行调整好画面，或是为整个项目选小范围帧导出一个预览）：
	- 选择帧范围（当用户输入全部帧时，提示用户可能会卡顿或崩溃）。

无论是 AniKit 缩略图生成，还是 CEP 插件里的导出为新文件，都要保持原坐标导出，模拟手动操作的话就是：复制元件 - 原位粘贴 - 记录坐标 - 缩放移动至舞台中央 - 导出序列帧 - 合成 WEBP - 还原坐标 - 保存文件（AniKit 的缩略图生成，则是直接关闭，不保存，避免修改到文件）。

## 04. 快速发送

支持将软件的工程文件直接发送到舞台，比如 PSD 直接发送到舞台，可能保留图层直接嵌入到另一个 PSD 文件里，支持 PSD 单个图层直接导出至软件内。

还是以 Animate 为例子。其他 AN 素材软件粘贴元件直接贴入舞台、跳过打开文件这一步，速度明显更快——原理是**预先把素材转换为 Animate 的剪贴板格式**，粘贴时由 JSFL 执行原位粘贴，全程不打开 fla。我们也采用这条路：

- **主方案（剪贴板预生成 + 一键粘贴）：** 点击发送后，AniKit 将该素材的剪贴板载荷写入系统剪贴板，经 WebSocket 通知插件执行 `clipboardPaste(true)` 原位粘贴。省掉了打开 fla 的数秒开销（进程启动、文档加载），粘贴近乎即时；坐标信息含在载荷内，原位还原无需用户对齐。
- **载荷来源（按优先级）：**
	1. 预生成缓存：导入或软件空闲时生成剪贴板载荷，存入 info 文件夹（伴生数据），发送时秒读秒贴；
	2. 实时转换：直接读取 fla（XFL 压缩包，库元件本身就是 XML）转换为剪贴板格式，不启动 Animate；
	3. 首次慢后续快：以上均不可行时，首次发送打开 fla 复制一次并缓存载荷，之后发送免打开。
- **技术验证（架构阶段最先行）：** Animate 剪贴板私有格式无公开文档——在 Animate 中复制元件后枚举系统剪贴板格式、导出内容，确认是否为 XFL 类 XML，验证转换可行性；验证失败则退回方案 3，体验一致。
- **兜底方案：** 载荷生成失败或复杂情况时，退回 WebSocket + JSFL 打开 fla 复制粘贴（慢但通用，即"打开 fla - 复制 - 原位粘贴到项目 - 关闭 fla"）。

这样就和我们原位导出时进行了联动：因为我们导出的文件保持坐标，粘贴时坐标可以准确还原，不需要用户再对齐。

#### 磁力链接技术分析

其他 Animate 素材软件的"磁力复制"内容（约 448 字节的 hex 串）分析：无可见明文结构（路径或 URL 直接编码会呈现明显规律），符合**加密载荷**特征——大概率是对称加密（AES 类）的 JSON 转 hex，载荷内含素材 ID、下载地址、校验信息；官网与本地库共用同一套密钥与格式，CEP 插件"磁力粘贴"时用相同密钥解密，拿到文件位置（云端下载或本地路径）后执行 JSFL 上台。加密的目的是隐藏真实下载地址、防篡改与防盗链。

结合"粘贴快、跳过打开文件"的现象，他们大概率在**服务器端预先把素材转换成了可直接粘贴的数据**：插件解密载荷后下载转换好的数据、写入剪贴板，用户粘贴即上台——所以官网里的素材也能一键磁力粘贴，因为转换是在云端提前完成的。

我们是本地自用软件，无需加密，降级方案（插件未连接时）：剪贴板载荷 = 明文 JSON（含 `anikit://item/{ID}`、文件路径、坐标信息），用户在面板中点击粘贴，插件读取后执行。

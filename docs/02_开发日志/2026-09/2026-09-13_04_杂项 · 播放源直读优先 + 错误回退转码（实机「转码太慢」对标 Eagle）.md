# 杂项 · 播放源直读优先 + 错误回退转码（2026-09-13，用户实机「转码太慢」对标 Eagle）

## 起因与定位

用户实机：一批 HEVC 视频（无限盲盒，ffprobe 实测 = hevc Main 1920×1080@30 + aac 48k 立体声，mp4 容器约 190MB/条）在 AniKit 里悬停 / 点开要等几十秒「转码中」，且每次开软件重来一遍；同一批文件 Eagle 导入即看、悬停即播。用户问"Eagle 是不是导入时做了转码"——不是，Eagle 根本不需要转码：WebView2 / Electron 同为 Chromium 媒体栈，经 Windows Media Foundation 可直解 HEVC（OS 有解码器即可，Eagle 能播证明本机有）。是我们自己的 ffprobe 探测分流（白名单只认 h264+aac/mp3）把本可直解的 HEVC 判成"不可直播"送进了 libopenh264 软编码转码。

## 修法：直读优先 + 播放错误回退（踩坑 075）

后端 `get_media_source` 加 `force_transcode` 参数（media.rs）：默认一律直给源文件绝对路径——零探测零等待，连每次必跑的 ffprobe 路由探测都省了；`route()` 白名单函数删除。前端四个播放点（HoverVideoLayer / HoverAudioLayer / previewMedia / TabLinks）接 `<video>`/`<audio>` error 事件：直读播放失败 → 带 `forceTranscode: true` 重调 → 后端转码兜底（每素材只回退一次，防循环）。previewMedia 回退期间复用 transcoding + 300ms 防闪的「转码中…」提示；悬停卡片转码期保持底层静态缩略图不闪。

效果：本机（Eagle 同机）这批 HEVC 视频从此零转码秒播；无 HEVC 解码器的机器 error 回退一次转码，产物在 cache/media 持久复用（上一轮的持久化改动与此配套——回退转码只发生一次）。

## 验证与文档

cargo test 446 全绿（route 两测试随函数删除，其余适配 force 参数）、pnpm typecheck 绿。PRD 04 播放解码定案、接口文档 18、踩坑 075 同步。**实机复验点**：悬停 / 点开无限盲盒视频即点即播不出"转码中"；任务管理器确认无 ffmpeg 长驻。

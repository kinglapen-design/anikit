# 杂项 · 转码产物持久化（cache/media）+ 最左侧插入提示修复（2026-09-13，实机复验两条）

同日二轮后用户实机复验再报两条：**每次打开软件 CPU 都长时间满载、加载慢**；**最左侧的插入提示没了**。

## CPU 高负载：转码产物随开库清空 → 迁 cache/media 持久化

用户问"解码不是 GPU 吗，CPU 怎么负载这么大"——播放解码确实是 WebView2 硬解，CPU 满载的真正来源是 **ffmpeg 转码**：WebView2 播不了的格式（HEVC / 特殊音轨等）要 libopenh264 软编码成 h264 兜底（大文件数十秒级，纯 CPU）。而转码产物放在 `cache/tmp`，属「会话级缓存、开库清空」（core/library.rs 清空名单）——每启动一次软件，上一会话的转码产物全被清掉，首次播放 / 悬停每个非直渲视频都重新转码，所以"每次打开都这样"。

修法 = 转码产物迁到 `cache/media/`（media.rs `transcode_source`），跨会话保留、不进开库清空名单。幂等性本就有 .stamp（源文件"大小:mtime秒"）保证，源变化自动重转，持久化无正确性风险。tmp 目录保留原口径（冲突弹窗预览 / undo 备份等仍是会话级）。cache/tmp 其余用途（导入冲突预览、文档 undo 备份、缩略图临时文件）未动。效果：每个非直渲视频全生命周期只转码一次。

## 最左侧插入提示消失：求交钳制误杀 → 横向改平移钳制

二轮给提示线加的 viewport 求交钳制把行首插入提示整条判空了：行首间隙 `g.left = -12`（layouts PAD.left = 0，首列卡片贴层左缘，行首间隙落在层外左侧 12px），横向求交后宽度为 0 → 不渲染。修法 = **横向平移钳制**（把竖块钉回视口左缘内显示，与 FolderStrip gapBar 同口径），纵向保持求交（行滚出视口不渲染）。PAD.left = 0 是现行布局（卡片贴视口左缘），行首提示线以 12px 半透明品牌色条贴在首卡左缘内显示。

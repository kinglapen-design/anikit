# 工作空间缓存文件名超长修复（2026-09-26）

## 起因

用户实机报：ws 里部分音频 / 视频缩略图生成失败（`ws_thumb_queue` WARN「工作空间缩略图生成失败（记入失败记忆）」），规律 = 中文长路径必败、同目录 ASCII 短名成功，ffmpeg / ffprobe 单跑全部正常。根因实锤：缓存文件名 = `encode_rel(rel)`（整条相对路径 URL 编码，**中文每字符 ×9 字节**）+ `-{mtime}-{size}.{ext}`——实锤案例 rel `02_创作/01_原创动画/01_计划中/224/01_灵感/05_音乐/不要去看天气预报.wav` 编码后**文件名 257 字符**，超 NTFS 单路径组件 255 上限，`fs::write` Invalid argument → `generate_thumb` 的 `.ok()?` 静默 None → 记失败记忆 → 落回格式图标。python 实锤 `\\?\` 长路径前缀也绕不过组件级限制（它只绕整条路径 260 的 MAX_PATH）。本任务纯后端缓存命名修复，无 UI 改动。

## 落地

- **有界命名（`services/workspace.rs`）**：缓存键茎 `job_key` 改 `{截断≤80的 encode_rel 前缀}-{fnv64hex(rel)}-{mtime_ms}-{size}`——前缀只截在完整 %XX 转义边界（编码串里 `%` 只作转义起始，回退至多两类半截形态）、只供人读；唯一性由 **FNV-1a 64bit** 兜底（手写十几行常量算法不加依赖；不用 DefaultHasher，跨工具链版本结果不稳定），定长 16 hex；mtime+size 仍内嵌判新鲜。全长 ≤ 80+1+16+1+21+1+20+扩展名 ≈ 150 字符。内容缩略图（cache_name）/ exe 文件级图标（icon_cache_name 改 `job_key + .icon.webp`）/ peaks / 失败记忆 / 队列去重共用同一 job_key 口径，`encode_rel` 收编为模块内私有编码原语。
- **purge_stale 改按 hash 段匹配**：截断前缀不再唯一，前缀 starts_with 旧口径作废，改 `-{fnv64hex(rel)}-` contains 匹配；按扩展名的格式图标（{ext}.webp）无此段天然不受影响。
- **peaks 同修（`commands/media.rs::card_peaks_by_path`）**：缓存名 `format!("{}.json", ws::job_key(...))` 同源复用，不再自行拼 encode_rel。encode_rel 其余调用方已全查（grep：仅 media.rs 一处落盘用途 + workspace.rs 自身，`.anikit/media/` 转码产物按 size+mtime 命名本就有界，格式图标按扩展名，均不涉及）。
- **存量迁移**：旧命名缓存全部失效成孤儿。thumbs / peaks 是纯缓存（PRD 可删可重建），`workspace.rs::migrate_cache` 以 `.anikit/cache_v2` 标志文件做一次性清理——开空间（`activate_space`，start_watch 前）标志不存在则清空 thumbs/ 与 peaks/ 后落标志；`.anikit` 其余内容（workspace.json / media/ 转码产物）不动；workspace/ 缺失或 .anikit 尚不存在的空间只落标志不清理（防下趟误清新命名缓存）；失败记忆进程级不落盘无需迁移。失败仅记日志不阻断开空间。

## 取舍

- 截断前缀保留可读性（调试 / 手清缓存时肉眼可辨），唯一性完全交给 hash 段——80 字符上限内不同 rel 前缀相同也无妨。
- 不做旧命名到新命名的逐个 rename 迁移：缓存内容不变也得按新键重写文件名，等价于重建；一次性清空最简单且 PRD 本就允许整删。
- 库侧 cache/thumbs、cache/peaks 按 assetId 命名不受影响；ws 转码产物按 size+mtime 命名有界不受影响。

# 重命名资源库落地（合并命名失误的补救口，2026-09-26）

## 起因

用户实机走查合并功能三连问：「合并之后命名以哪个为主？命名失误了怎么办？有重命名库的功能吗？」——答案：合并后名字以**目标库**（勾选集中 order 最前者）为准、库内内容一律不改名；命名失误此前无补救口，重命名功能不存在。本轮补上。

## 落地

- `core/space.rs` `rename_library`：库目录改名 + libraryOrder 同步（save_space 单写点）；新旧同名 no-op；非法名 / 空间保留名 / 撞既有目录拒绝。
- `core/config.rs` `rename_library_entry`：全局配置最近列表按旧 path 同步 name + path（纯逻辑 `rename_entry_in` 可单测；命令层调用，失败仅记日志不回滚——改名已生效）。
- `commands/library.rs` `rename_library`：编排 = space 改名 → relations.json 端点 lib 名改写（复用合并的 rewrite_lib_refs，folder_map 空——档案 id 不随库改名变）→ config 同步；改名的是当前打开库时**内存 root 原地更新**（全部路径经 lib.root 现取，不切库不重启、不清会话缓存），返回其最新 LibraryInfo，否则 null。
- 前端：`CreateLibraryModal` 加改名模式（prop `renameFrom`：标题换「重命名资源库」、预填旧名、同名拦「名称没有变化」）；菜单「仓库 ▸ 资源库」加「重命名当前资源库」（无当前库禁用）；预览页补改名模式实例。

## 验证

cargo test 506 绿（新增 4：space 改名全链 / 命令层非当前 + 当前两路径 + 校验组 + config 纯逻辑）；clippy 零告警；typecheck 绿。未实机走查（交用户）：菜单改名弹窗观感 / 当前库改名后侧栏库名与菜单对勾同步。

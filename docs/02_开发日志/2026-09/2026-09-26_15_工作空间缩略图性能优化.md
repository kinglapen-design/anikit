# 工作空间缩略图性能优化（worker 池 + 去重 + 失败记忆 + 视口优先，2026-09-26）

## 起因

工作空间（ws）缩略图链路六根热埂逐一查实：每张图全尺寸解码再缩小（image crate 无 DCT 缩略解码，24MP 图全量解码 + 大中间缓冲）；每次 `request_workspace_thumbs` invoke 裸 spawn 一条新线程、线程内严格串行 for 逐张生成，两条线程可对同一文件重复解码；前端 `requestMissingThumbs` 整目录缺失项全量发、无视口裁剪，fs-changed 去抖重扫又重复补发；音视频逐文件 spawn ffmpeg 串行；`list_workspace_dir` 同步 IO 跑在 tokio worker 上；解码失败无记忆——thumbPath 恒 null 的条目每次重扫重新请求、重新失败、无限重试，前端也只有空盒。

本任务纯性能优化（不换解码库、不加依赖、不动库侧导入/预览链路、不做内存 LRU），按 A/B/C 三项落地。

## 落地

### A. 后端生成并发化 + 去重 + 失败记忆

新建 `services/ws_thumb_queue.rs`（仿 preview_queue / anim_preview_queue 的自管 worker 结构，非 rayon par_iter——任务来自持续到达的请求事件流，需常驻队列 + 插队，不是一把批处理）：

- **固定并发 worker 池**：N = 可用并行度一半钳 1..=4，Condvar 常驻空闲零 CPU；音视频 ffmpeg 子进程随之从串行变至多 4 并发。
- **跨请求去重**：键 =（workspace 根, 缓存键茎 rel+mtime+size，与缓存文件名同源的 `job_key`），队列中 / 进行中已有同键跳过——fs-changed 重扫与视口补发的重复请求归零；worker 执行前再重查一次新鲜度（排队期间可能已被另一趟生成）。
- **失败记忆**：进程级 `HashSet<(根, 键茎)>` 存 workspace.rs（缓存域归属）；worker 解码失败记入，入队解析（`resolve_thumb_job`）命中即跳过，本会话不再重试；源文件 mtime/size 一变键自然失效会重试；成功路径防御性清除（瞬时故障自愈）；进程级不落盘，重启后每失败条目至多再试一趟。
- **失败条目落回格式图标（用户可感知变化）**：原失败条目恒空盒。现两路落回系统格式图标（与 fla/txt 等不可解码类型同口径、按扩展名缓存）：worker 失败当场生成图标随 `workspace-thumbs-ready` 带回（`ThumbReady` 新增 `thumbKind` 字段，`formatIcon` = 失败落回项，w/h 带图标边长但前端忽略）；列举时 `entry()` 命中失败记忆视同不可解码走既有图标分支。**WsEntry 不加字段**——失败状态复用 thumbKind=formatIcon + 图标 thumbPath 表达，前端 thumbPath 非 null 天然不再请求，是「WsEntry 加字段 / 负载带失败项」两案之外改动最小的形态。
- **批量回吐**：凑满 16 条或队列完全排空（busy==0 且 pending 空）emit 一帧，大目录首开不再每 invoke 一条线程一事件；切空间（start_watch）清 pending 并同步摘去重键，进行中的任务落盘幂等无害。

原 `request_thumbs` 串行入口退役为 cfg(test) 同步镜像（语义同 worker：同过滤、成功清记忆、失败记记忆），既有测试零改动继续生效。

### B. 列举挪出 tokio worker

`list_workspace_dir` 与 `request_workspace_thumbs` 两命令改 async + `tauri::async_runtime::spawn_blocking`：目录列举的同步 IO 与 exe 图标 COM 提取（SHELL_ICON_LOCK 保留）不再占 tokio worker（饿死帧流 WS 等异步任务的隐患）；后者入队前的逐条 stat / 新鲜度判定同挪。

### C. 前端视口优先

虚拟滚动本就只渲染视口 + 800px buffer 的卡——复用既有可见性设施，最小实现：AssetCard 的 IntersectionObserver `cardVisible` 为真且缺缩略图的 ws 卡上报 `ws.requestVisibleThumbs`（卡片按 assetId 作 key 不复用，挂载即视口邻近）；ListRowCard 无观察器，挂载即上报。store 内 120ms 固定节拍合批（不用去抖——连续滚动时去抖永不到点）发 `priority=true`，后端整批插队队首保批内顺序；`loadDir` 的全量缺失请求不变、排队列尾部后台补发。恢复滚动位置落在目录中部时可见卡不再等前面全部生成完。`patchThumbs` 改按负载 `thumbKind` 回填，仅 asset 项补 w/h（图标见方不代表源比例）。

## 取舍

- 解码本身（全尺寸解码 + Triangle 重采样）不动——并发化已是数量级收益，换库另立项。
- 失败记忆进程级不落盘：损坏文件重启后重试一趟的代价换零维护；落盘即多一份要判新鲜/清理的索引，不值。
- 失败图标提取本身失败（无关联程序）时不上事件，条目维持空盒待下次列举落回——边角不追求完美即时性。

## 验证

cargo test 541 绿（新增：`ws_thumb_queue` 五件——worker 数钳位 / 插队保序纯函数 / 在途与新鲜去重 / 失败记忆不再重试 / 池全量完成；`workspace` 一件——失败条目列举落回格式图标 + 源变化键失效回待生成，`request_thumbs_filters_and_skips_failures` 补失败记忆重试断言；损坏样本 = IDAT 数据字节原地翻转，文件头完好 probe 可探测、CRC 失配 decode 必败）；`cargo clippy --lib --all-targets -- -D warnings` 零告警；`pnpm typecheck` 0 错。

耗时对比（临时探针实测，测完即删）：12 张 4000×3000 PNG 首开——旧串行 1007ms vs worker 池 284ms ≈ **3.5×**；实机大图 JPEG（全尺寸解码更重）与低速盘差距更大，且首开/重扫不再随文件数线性堆线程与重复解码。实机走查交用户：大目录首开可见区先出图、滚动跟手补发、损坏文件显示格式图标不再空盒。

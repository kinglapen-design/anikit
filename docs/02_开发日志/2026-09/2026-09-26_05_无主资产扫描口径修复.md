# 无主资产扫描口径修复（空间级引用集，2026-09-26）

## 起因

用户实机两连报：空间内新建第二个资源库，弹「发现 908 个无主资产文件」（全是另一库的资产）；切回旧库又报新库刚导入的 1 个无主。用户问"是不是没做隔离、需要多建 assets"。

## 定性

不需要多建 assets——空间级统一素材池是设计本身（删库孤儿清理、资源库合并都建立在共享语义上），坏的是**无主扫描的判定口径**：assets 池 2026-08-12 已上移空间级，但开库自检的无主扫描（2026-09-03 随资产污染修复落地）引用集仍按当前库 folders ∪ recycle 判定——池是空间级、判定是库级，凡他库引用的资产在当前库视角全是"无主"。单库空间时代隐形，多库一建即爆（踩坑 090）。

孤儿只弹清单不自动删，两连报全程零数据损失。

## 修复

- `core/space.rs` 新增 `referenced_assets_space`：空间内各库 folders ∪ recycle 磁盘态并集；任一库读取失败即报错。
- `core/library.rs` 开库自检：引用集 = 空间级并集 ∪ 当前库内存态（自检修复未落盘的窗口期保守兜底）；`scan_orphan_infos` 签名改传引用集（`Option`——并集构建失败 = 某库数据文件损坏 → 跳过孤儿判定只清空壳，**宁可漏报不可误报**：误报会诱导用户清掉他库资产）。
- 弹窗文案顺手修正：「残留在素材库目录中」→「残留在素材池（assets）中，但全空间各库的数据层都没有对应记录」（池是空间级，原文案库级误导）。
- 对照删库孤儿清理 `library_orphans`（一开始就是各库并集）——口径已天然正确，不动。

## 验证

cargo test 501 绿（新增 `open_orphan_scan_uses_space_wide_references`：两库空间，仅邻库引用的资产不报、全空间无引用才报；原单库测试语义不变照旧过）；clippy 零告警；typecheck 绿。未实机走查（交用户）：多库空间新建 / 切换库不再误报。

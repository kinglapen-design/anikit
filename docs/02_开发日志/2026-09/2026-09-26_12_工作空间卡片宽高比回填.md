# 工作空间卡片宽高比回填（视频/音频卡方盒裁切修复，2026-09-26）

## 起因

用户实机报：工作空间视口的视频卡片画面被上下裁切。ws 视口与库视口共用 AssetCard 渲染链，卡片盒子宽高比来自 `useGridLayout` 的回退链 `thumbW → w → 300 方盒`，缩略图 `object-fit: cover` 铺满盒子。库侧视频导入时 ffprobe 写入了真实宽高，盒子比例 == 视频比例，cover 不裁；ws 侧 `services/workspace.rs entry()` 只对图片跑魔数探测（非图片返回 None），视频/音频的 w/h = null → 回退 300 方盒，16:9 首帧缩略图铺进方盒被上下裁掉。

## 定性

ws 条目并非没有真实比例可得——视频首帧 / 音频波形 / 字体样张缩略图本身就与源同比例，缓存在 `workspace/.anikit/thumbs/`。定案不从 ffprobe 拿宽高（列目录逐文件 spawn 子进程太慢），改从**已缓存缩略图自身尺寸**拿比例（布局只需要比例，缩略图尺寸即够）。首开目录（无缓存）先方盒占位、缩略图就绪后自动变真实比例；再次进入（有缓存）列目录即正确。

## 修复

后端 `services/workspace.rs` 两条通道补齐宽高：

- **列目录命中新鲜缓存**：`entry()` 在 `fresh_thumb_path` 命中且 w/h 尚为空时，对缓存的 webp/png 缩略图做仅文件头的尺寸读取（`image::image_dimensions`，不全解码），成功即写入 WsEntry 的 w/h。图片条目维持现有魔数 probe 路径不动（`w.is_none()` 守卫天然不覆盖图片源探测值）。
- **后台生成完成**：`ThumbReady` 事件负载加 `w/h`（`generate_thumb` 里 shrink 后尺寸本就已知，顺手带出），`workspace-thumbs-ready` 负载由 `[{absPath, thumbPath}]` 变为 `[{absPath, thumbPath, w, h}]`。

前端 `stores/ws.ts patchThumbs` 回填 thumbPath 的同时，对 w/h 为空的条目补上事件带回的尺寸（图片条目已有源探测值不覆盖）；条目换新数组触发响应式，`useGridLayout` 的 items watch 自然重排恢复真实比例。`wsOps.ts` 的 `WsThumbReady` 类型同步加 `w/h`。`wsEntryToPlacement` 无需签名变化——w/h 本就直通 PlacementView，仅注释口径更新。

音频/文本/字体卡不受此影响（2026-09-22 定案：填充型卡片布局固定比例 音频 2:1 / 文本 5:4 / 字体 1:1，`useGridLayout` 不读它们的 w/h），本次主要受益是视频卡。

## 验证

cargo test 531 绿（新增 `list_dir_backfills_dims_from_cached_thumb`：伪造不可解码 mp4 + 手写 640×360 缓存 png，验证无缓存时 null 回退、缓存新鲜时文件头回填 640×360 且 thumbKind=asset；`thumb_freshness_tracks_mtime_and_size` 补事件负载宽高与「图片条目维持源探测尺寸不读缓存」断言）；pnpm typecheck 0 错。全量首跑曾撞 `commands::preview` 帧条测试一次性 UnexpectedEof——既有抖动（wait_until 只等文件存在不等写完，读到半成品 webp），与本改动无关，单跑与全量复跑均绿。实机走查交用户：首开目录方盒占位 → 缩略图就绪自动变真实比例；再次进入列目录即正确。

# 2026-09-22_01 分组名称规则匹配词干修复（P4⊂mp4 案）

> 用户实机问：P5A_01.mp4 为什么归进 P4 组，非要把 P5 组移到 P4 上面才能正确分组。根因不是归组裁决逻辑，是名称规则的匹配对象错了。

## 根因

归组名称规则（`src/lib/grouping.ts` `ruleHits` / `ruleWeight` name 分支）对**含扩展名的完整显示名**做子串匹配：`"p5a_01.mp4".includes("p4") === true`——"p4" 撞中的是扩展名 ".mp4" 里的 "mp4"。P5A_01.mp4 因此同时 AND 命中 P4 组与 P5 组，且两组权重都是 2（ext 1 + name 1），平局按定义顺序先建者优先 → P4 在前归 P4。P3_01.mp4 同样命中 P4 组规则，只是 P3 组排最前把它"救"下，所以只有 P5 露馅。9-17「命中关键字更多者」修订（P1 vs P1_2K 案）治词数不同的平局，治不了本坑——匹配对象本就不该含扩展名（扩展名归属有专门的「扩展名」规则）。

## 改动

`src/lib/grouping.ts`：新增 `nameStem`（去最后一个 "." 后缀；点开头 / 无点取全名），`ruleHits` 与 `ruleWeight` 的 name 分支同步换词干匹配。PRD `02_文件整理/04_分组.md`「自定义规则」补口径「匹配对象为词干，不含扩展名」。踩坑记 [082](../../04_踩坑记录/061-090/082_名称分组规则匹配全名——P4撞中.mp4子串，归组误判且随组序漂移（2026-09-22）.md)。

## 验证与未验证项

`pnpm typecheck` 绿；node 模拟三组场景（P3/P4/P5 各 = ext{mp4} + 名称{PX}）：P3_01 / P4A_01 / P4B_02 / P4C_01_2K / P5A_01 各文件唯一命中本组，归组与组序脱钩；P1_02_2K 案不回退（"2k" 在词干内真命中，{P1,2K} 2 词仍胜 {P1} 1 词）。未验证项交实机走查：原库 P5A_01.mp4 应直接归 P5 组（组序任意）；存量「名称分词恰好含扩展名子串」的旧配置行为随之纠正（如分词 "mp4" 不再匹配一切——该需求应改用扩展名规则）。

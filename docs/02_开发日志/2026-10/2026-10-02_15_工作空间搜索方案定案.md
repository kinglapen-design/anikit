# 工作空间搜索方案定案（Everything + 自研爬盘回退，2026-10-02）

用户咨询「工作空间能否整合 Everything SDK 提速搜索、文件夹数量标记能否借 NTFS 索引低成本接入」，三轮讨论后拍板立项（下个会话做），纯方案轮零代码。方案全文 = 待办 2026-10-02，PRD 02 / 03 同步。

## 现状摸底（为什么需要）

- 工作空间无任何索引：懒列举单层 `fs::read_dir`（`services/workspace.rs list_dir`），无递归计数接口；搜索只有库侧（内存 HashMap 分词子串，`services/search.rs`），ws 视口搜索恒空（match-all 分支 + `ws:` 假 id 永不命中）——即 PRD 02 步骤 3「搜索搁置（无 Everything 级速度不接，另行立项）」的搁置状态。
- 数量标记只有前端已加载目录的直接文件数（`stores/ws.ts fileCount`），TreeRowItem 的 count / directCount 双口径渲染位现成，缺的只是数据。

## 调研结论

- **Everything 可集成且口径恰好匹配**：查询语法原生空格分词 AND，仅命中文件名 / 路径（= PRD 03 对 ws 搜索的既定口径）。数量标记走「一次性聚合」——一条 `path:root` 全量查询拿回全部后代，内存一趟聚合出每文件夹直接 / 递归计数，10 万条约 10–20MB 一次 IPC 拷贝，可接受。
- **集成方式定手写 IPC**：官方 SDK 只是 WM_COPYDATA wrapper 且 DLL 再分发条款不明；es.exe 每次查询起进程不适合批量场景。1.4 协议 = FindWindow + WM_COPYDATA（自建 message-only 接收窗），1.5 = SDK3 命名管道（实测快至 20 倍 + GET_FOLDER_SIZE + index journal，列二期增强）。项目已有 `windows 0.62` 与大量手写 Win32 先例，零新增二进制依赖、零分发授权问题。现成参照 = Windhawk better-file-sizes 模块（含 reparse point 处理实测）。
- **Windows Search 被否**：索引默认只覆盖用户配置文件夹 / 库，工作空间任意路径大概率未索引——OLE DB（Search.CollatorDSO）查空、WinRT StorageFolder 退化爬盘还多 COM 开销；爬 scope 编程接口（ISearchCrawlScopeManager）会引入 SearchIndexer 资源占用骂名。回退搜索不押它；`search-ms:` 协议留作右键「在资源管理器中搜索」顺手项。
- **junction 是近忧**：reparse point 子树在 Everything 里按真实目标路径建档（junction 路径下查不到），方向 b（2026-10-01 定案下会话开工）的路径映射表与本立项共享，宜同期设计。

## 定案

**双层架构**：Everything 层（探测到 = 搜索 + 数量标记全功能，手写 IPC + 能力探测降级）/ 自研爬盘回退层（无 Everything = Enter 触发慢速遍历搜索，rayon + 流式 + 进度 + 可取消；数量标记维持现状不递归补）。**首启引导页加 Everything 官网推荐安装**（用户定：目标用户基本人手一个 Everything）。降级语义与 ffmpeg 能力探测同款，主功能零影响。

# 2026-10-24 语义分析方案定稿与 spike 开工

## 用户定案

1.0 收尾第 2 项“向量分析”不再按旧的“整段抽帧 + 图像向量平均”推进。产品采用 Topaz 式分层：AniKit 内置可免费离线使用的基础语义能力，高成本视频理解交给外部 provider，由用户知情选择性能、费用和隐私代价。

内置基础层使用中文图文对齐 CLIP，CPU 默认、GPU 可选；不内置 LLM，不安装或启动 Ollama，不把 PyTorch / CUDA 大环境引进 APP。外部 OpenAI 兼容服务与 Ollama 只负责详细动作描述、有序事件和可选推测，未配置时不影响基础画面搜索。

## 技术与数据边界

视频、动图和序列帧按真实时间轴分段并保留帧向量，命中的是“素材 + 起止时间”，不是整段视频一个平均向量。外部返回的中文描述与事件仍由本地同一 CLIP 文本塔编码，因此详细分析后搜索可离线进行，也不需要外部 embedding 的第二套向量空间。

本地只保存可重建的 SQLite 向量 / 片段 / 事件 / 任务索引；模型按固定 revision 独立管理。分析由用户手动选择素材或文件夹触发，独立 worker 支持暂停、恢复、取消、重试和重启续跑，不默认导入后自动全库分析。先后关系与因果推测分栏，后者必须标明不确定性。

搜索保持原分词契约，新增独立语义服务。每个 Placement 只显示最佳片段及命中数，其他片段经菜单选择；预览复用现有 seek / setFrame，动图和序列帧额外保存帧索引，避免平均帧率误跳。

## Spike 开工口径

主测 Chinese-CLIP ViT-B/16，RN50 作轻量对照；首轮 FP32、静态输入、batch 1。运行时验证 Rust `ort` + 统一 ORT DirectML 1.24.4 / DirectML 1.15.4 动态库（官方 win-x64 文件约 36MB），`api-24`，CPU 与 DirectML 使用同一份 ONNX，不采用 CUDA 作为默认路线。

验证分三层：官方预处理与 token IDs、真实模型输出与向量误差、中文查询和 hard negatives 排名。GPU 必须记录实际 EP，初始化或运行失败明确回退 CPU，不能伪报加速。首轮还要验证 DLL 私有分发、模型冷启动、文本 / 图像耗时和内存。

Chinese-CLIP 代码为 MIT，但当前 HF 权重元数据未声明许可证；许可未确认前只做内部验证，不打包、不重新托管。模型交付采用首次启用明确下载 + 离线模型包，完成后基础能力可离线使用。

当前库按名称没有“机器人 / 洗碗 / 厨房”现成样本，不能用模型跑通代替语义验收。后续验收集可采用 [BridgeData V2](https://rail-berkeley.github.io/bridgedata/) 的机械臂厨房 / 水槽轨迹和人工标注（官方 CC BY 4.0），补“主体对但动作错 / 动作对但主体错”的负例。

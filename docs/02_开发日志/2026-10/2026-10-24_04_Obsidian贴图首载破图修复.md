# 2026-10-24 Obsidian 贴图首载破图修复

## 现象与定位

用户实机反馈：Obsidian 截图粘贴后，图片确实已进入 AniKit，但文档里显示破图；重启后又能显示，因此每次粘贴都被迫重启。现场链接的 `http://127.0.0.1:17701/item/by-name/...` 在事后请求返回 `200 image/png`，说明链接和文件内容都没有坏。

根因是首次请求早于自动导入完成。收件箱监听要求文件静止 2 秒，再以 500ms 节拍完成两轮大小与可移走探测，通常约 3 秒才进入导入管线；插件却在粘贴当刻写入链接，Obsidian 随即请求图片。旧媒体端点查不到 originName 就立即返回 404，图片元素保留失败结果，重启重新请求后才恢复。

## 修复

新增 `services/media_source.rs` 承接图片源解析与 by-name 查询。导入途中的暂态未命中改为每 100ms 重查一次，最多等待 10 秒，让第一次 HTTP 请求直接等到真图，而不是把暂态 404 交给编辑器。等待和读盘都不持库锁；库未打开立即报错，超过等待上限仍返回 404。

`server/media.rs` 只保留 HTTP 状态映射和字节响应，按 ID 与按名两种端点共用同一图片源实现。插件生成的 Markdown 和 by-name 链接均不需要改写，Typora 与 Obsidian 同享修复，也不采用写死延迟 3 秒的脆弱方案。

## 验证

新增回归测试以独立临时素材库驱动真实导入管线：查询先发起，图片延迟 300ms 才导入，最终同一次查询取得 `image/png` 和与源文件一致的字节，0.36 秒完成。测试不接触用户素材库。

全量验证：后端 653 项通过、0 失败、13 项按既有规则忽略；`cargo check`、Clippy 和 `pnpm typecheck` 均通过。免安装包重打与 HTTP 冒烟另记当日打包日志。

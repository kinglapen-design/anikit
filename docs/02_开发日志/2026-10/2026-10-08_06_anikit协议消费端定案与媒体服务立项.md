# anikit:// 消费端定案与媒体服务立项（2026-10-08）

纯方案轮零代码。起因是用户问「anikit://item/ 和 anikit://folder/ 有哪些消费端」，五轮讨论后拍板立项，实施六步记 [待办 2026-10-08](../../03_项目进度/待办细节清单/2026-10-08.md)。

## 现状核查：消费端三层全空

全库核查结论（与 2026-08-21_04 那次核查一致，至今未变）：`anikit://item/{ID}` / `anikit://folder/{ID}` **只有生产端没有消费端**——唯一出处是 menuOps.ts 右键「复制链接」把文本写进剪贴板。前端无任何解析跳转代码；系统协议未注册（tauri.conf 无 protocols、Rust 无 deep-link）；详情 links 字段只读展示首条（TabBasic），后端 shell_open 的 open_url 只放行 http/https，anikit:// 传过去也会被拒；MCP 工具直收 assetId/folderId 不经 URI；CEP 插件无引用（旧剪贴板降级载荷方案 2026-09-25 已废）。

PRD 侧的承诺其实不少（01 的 ID 寻址改名不死链、02-09 的点击跳转、接口文档的外部调起），代码侧一个都没落——协议处于「只产不消」状态。

## 定案一：外部 MD 用图 = 本地 http 媒体服务，废弃路径方案

用户场景：写 MD 文档时想用链接插入图片，最好不用 Obsidian 插件、任何文本编辑器通用。外部参照：Eagle 有 `eagle://item/{文件名}` 系统协议（文件名寻址会死链，我们 ID 寻址已优于它），第三方 Eagle-Obsidian 方案是「复制图片进 vault + callout 回链」的混合路线。

讨论中摆了两条路线：路线 A = 本地 http 图片服务（图片留库单份存储、ID 寻址改名不死、改图同步，代价是 AniKit 没开图全裂）；路线 B = 导出副本进 vault（文档自包含，但图片脱库双份存储）。用户先倾向「复制文件路径最稳、AniKit 没开不掉链」，被两个事实纠正后拍板废弃路径方案：**我们的磁盘名随重命名变化**（路径写进文档就开始倒计时，这正是 PRD 01 定 ID 寻址的原文理由），且 **Obsidian 默认不渲染 vault 外本地路径图片**；更本质的是用户自己补刀——info 文件夹跟黑箱没区别，路径不可辨认，「要发别人在里面找图片会非常痛苦」。

定案：**起本地 http 媒体服务**（与 MCP 同 axum 实例，17701 端口优先），`GET /item/{id}` 按 ID 实时解析磁盘路径返回图片字节。右键「复制 MD 图片」生成 `![名](http://127.0.0.1:{port}/item/{id})`，Obsidian / VS Code / Typora 预览全渲染，零插件全编辑器通吃。端口纪律：MCP 既有「被占回退动态端口」对写死在文档里的 URL 是灾难，复制时若实际端口 ≠ 17701 须 toast 提醒「端口被占，链接重启后可能失效」。

## 定案二：内部 MD 编辑器渲染层解析，点击行为与源码分离

内部 MD 编辑器（PreviewText）早就立着 09 待办「库内资产引用解析」（md 图片引用渲染占位文本）与「md 链接不可点」。用户问「内部点击跳转不需要图片套链接就可以直接跳转吧」——对，渲染管道是自己的 markdown-it，行为在渲染层随便加：渲染 `![](anikit://item/{id})` 时归一化解析 ID → convertFileSrc 显示真图，点击 = 内部跳转选中，**源码保持裸图片语法**（套链接 `[![]()]()` 只在外部场景才有意义）。配套：编辑态粘贴 anikit:// 链接自动补全 `![]()` 语法。渲染层与打包导出共用一个归一化解析器，认双形态（anikit:// 与 http://127.0.0.1:*/item/{id}——外部复制回来的 http 链接粘进内部文档同样能渲染、能打包）。

## 定案三：链接图标快捷入口搁置

用户回忆设计稿里详情链接区块有个小链接图标，本意是「剪贴板里是链接时点图标直接创建链接文件」。讨论后用户自评「不如复制粘贴文件来得快，只是多个入口，不知道有没有意义」——**搁置不做**。

## 定案四：links 输入框可编辑 + scheme 分流跳转

TabBasic 链接输入框从只读占位转正：补编辑链路（AssetMeta.links / ArchiveData.links 数据层字段早有，缺写命令与前端输入）；点击按 scheme 分流——`anikit://item|folder` 前端解析内部跳转（选中 + reveal），http(s) 才走 open_external_url；shell_open 只放行 http/https 的安全边界保持不动，内部跳转不经过它。

## 定案五：MCP 增强 = 参数吃 URI + 返回附 uri

用户现状：复制 anikit:// 链接发给 AI，AI 从 URL 抠出 ID 再调 get_asset_detail 能跑通。增强把这个「抠」的动作收进服务端：①所有收 assetId/folderId 的工具参数加 URI 归一化（`anikit://item/xx` → `xx`），AI 整段透传用户粘贴的链接即可；②search/detail 返回附 uri 字段（http open 形态，AI 回复里可点击）。MCP Resources（协议原生资源机制）评估为增量收益小、rmcp 支持度待查，不做。传图纪律不变（AI 看图走 thumbPath，不经协议传字节）。

## 定案六：deep-link 系统注册废案，/open 端点全替代

PRD 09 的 2026-08-21 旧定案「安装时向系统注册 anikit:// 协议处理（Windows 注册表 / macOS Info.plist），协议注册 + 单实例收链接随阶段九同批」**作废**。用户问「只为了跳转还有必要做 deep-link 吗」——没必要：媒体服务反正要起，顺手加 `GET /open/item/{id}` 端点就覆盖全部点击跳转场景（外部 MD 回链、AI 回复链接）：点击 → 浏览器开一个极简页（「已在 AniKit 中定位，可关闭本页」）→ AniKit 收到请求内部跳转 + 主窗口前置。deep-link 唯一增量是「少开一个浏览器标签」，不值注册表写入（portable 绿色语义冲突）+ 单实例参数转发的工程量。

由此形成**双形态分工**（本轮核心定案）：

- `anikit://item/{id}` = **内部标识符**——复制链接 / links 字段 / 内部 MD 引用语法 / MCP 工具参数，只在 AniKit 内部解析消费，永不经系统。
- `http://127.0.0.1:{port}` = **对外可点击形态**——`/item/{id}` 图片渲染 + `/open/item/{id}` 点击跳转，外部编辑器、AI 客户端通吃，零注册零插件。

## 定案七：打包导出归 AniKit 侧，工作空间直通免导入

用户问 MD 没有 AE 那种收集打包功能、散落引用项发给别人怎么办——任何引用形态发出去都死（本地路径指向你的盘、127.0.0.1 指向对方自己的电脑），唯一自包含做法 = 图片随文档走。这件事 AniKit 做比编辑器插件有优势：它认识双形态引用，能按 ID 实时找到图片本体。定案：内部 MD 编辑器出「打包导出」——解析文档引用 → 图片导出文档旁 `assets/`（文件名用资产名可辨认）→ 链接改写相对路径，即 AE 打包的 MD 版。用户随之洞察闭环：外部编辑器写的 http 引用文档，最后一步可以在 AniKit 里打开打包——且若文档本就放在工作空间（索引式真实目录），AniKit 直接可见，**右键打包免导入**。完整工作流：外部编辑器写文档（http 引用图片）→ 文档在工作空间里 → AniKit 打包 → 发送。

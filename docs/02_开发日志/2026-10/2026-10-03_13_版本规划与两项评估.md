# 2026-10-03_13 版本规划与两项评估（纯方案轮零代码）

## 用户版本规划（登记路线图「1.0 迭代」节首）

1.0 收尾五项 → 传 GitHub：工作空间搜索（下个会话做）/ 筛选 / 向量 / 设置面板 / 文档撰写（教程 / API / 关于）。0.2.0 = 插件市场 + 格式支持插件化（改架构）。0.3.0 = 内置简易 Agent（大概率）。搜索开工要点两条已补进待办 2026-10-02：ws 搜索框删筛选钮（查实：筛选钮**全局未接业务**，FloatBarHost 点亮占位；ws 无附加数据可筛整颗隐藏，组件需补 filters 空即不渲染）+ 超级全局 1.0 不做。

## 评估一：体量与可维护性（用户问「搞完是不是到大型了，后期还能维护么」）

现状体量：Rust 4.2 万行 + 前端 5.2 万行 ≈ 9.5 万行代码，文档 110 万字符——中型上沿；1.0 五项完成估计 11–12 万行，刚进大型门槛。结论 = **到得了大型也维护得了**，依据 = 架构收敛点已成型（命令层 / 单写点 / 适配器层隔离）、文档体系（PRD 先行 + 接口随码 + 踩坑 100+ 防复发 + 一任务一文件）压低了跨会话成本、570 后端单测 + 探针族成回归网。真正决定后期生死的是 **0.2.0 插件化**——全项目最大一次架构手术（格式链路抽象为可插拔），插件边界（清单格式 / ABI 版本 / 隔离级别）必须一轮定净并立边界文档，不赶工；0.3.0 Agent 的新状态面有 MCP 写入闸地基兜底。

## 评估二：超级全局搜索（库 + 工作空间一键同搜，用户问难不难、难则不考虑）

难点不在后端（库分词已落地、ws 双层下个会话做），在融合层三个新决策：混排结果视口（新视口型）、两路异构结果相关性统一、数量级差异截断分页（ws 命中数千 vs 库几十）。交互层现成（右键 / 拖拽 / 预览 / 详情已按 ws: 前缀分流）。估计 2–3 个会话起步——**1.0 不做（用户拍板）**；库搜库 / ws 搜 ws 行为对齐覆盖绝大多数场景，0.2.x 底座清晰后再评估。

# 2026-11-06 卡顿治理：undo 快照字节预算 + 子窗口族共享 UDF

用户报「软件突然变得这么卡顿，拖拽整理偶尔也拖不动」，截图 = 主窗口「未响应」。本轮按实证线索治两个内存/资源放大点；拖拽链路本体未改（11-04 跨窗口快速拖出竞态修复已在包里，本轮未找到新回归证据）。

## 实证线索

- **主进程内存随操作线性增长**（11-04 排查坐实）：undo 栈 50 步 × 整份 folders.json 前后快照无字节上限（当前库 folders.json 约 1 MB → 50 步 ≈ 104 MiB），是「启动 18 MB → 晚间 150-200 MB」的主因。
- **子窗口每 label 独立 UDF**（踩坑 121 的 Runtime 156 规避）= 每子窗口一份完整 browser process，多开预览/插件窗即进程与内存膨胀。

## 修复

**① undo 快照总字节预算**（core/undo.rs）：`MAX_SNAPSHOT_BYTES = 64 MiB`——undo + redo 两栈 before/after 快照合计超预算即淘汰最旧（undo 先淘汰，redo 是最近撤销的工作保；undo 空了仍超才淘汰 redo）。50 步数限 + 64 MiB 字节预算双限，主进程内存随操作进入平台期；commit / undo / redo 后均执行预算。新增测试 = 40 步 × 2 MiB 超预算 → 淘汰至预算内且最旧步已丢、撤销仍可用。

**② 子窗口族共享 UDF**（踩坑 121 后续）：child_data_dir 由「每 label 一份」改「子窗口族共享一份」（`EBWebView-children`，与主窗口隔离）。dev 实窗验证：插件窗 + 预览窗（两个不同 label）同开正常、日志无 wry ERROR——**Runtime 156 接受「主窗口 + 子窗口族」两 UDF，族内多 environment 也接受**。进程膨胀从「每窗一份」降为「族一份」。
